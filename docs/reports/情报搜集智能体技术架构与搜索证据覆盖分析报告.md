### 1.2 技术结论摘要

当前项目已经建立了一条完整的公开信息调研主链：

```text
Task
  → Research Question
  → Search / Crawl / Document
  → Fact / Evidence
  → Semantic Review
  → Coverage / Conflict
  → Material Digest
  → Research Report
```

这条主链已经解决了“信息如何成为正式报告中的可核验结论”问题。其最有价值的部分不是搜索引擎数量，而是事实、证据、审核、覆盖和报告之间的确定性约束。

当前主要矛盾已经转变为：

> 如何在单机、本地模型、有限公网访问和有限 Token 预算下，稳定发现高价值候选，并将其转化为覆盖关键问题的独立有效证据。

因此，后续优化重点不应是继续扩大抓取数量或上下文窗口，而应建设四项控制能力：

1. **问题 × 来源角色的证据覆盖矩阵**；
2. **覆盖缺口驱动的下一动作选择**；
3. **跨查询、跨引擎的统一候选治理**；
4. **Evidence Gain 驱动的停止与评测体系**。

## 2. 系统定位与目标分析

### 2.1 系统定位

本项目定位为面向公开互联网信息的本地情报搜集与调研 Agent。用户提供主题、目标或核心问题后，系统自主完成问题拆解、信息发现、资源获取、内容提取、事实核验、缺口判断和报告交付。

普通 Research Agent 的典型目标是：

```text
用户问题 → 搜索与阅读 → 综合回答
```

情报搜集智能体的目标是：

```text
用户情报目标
  → 关键问题
  → 系统性探索信息空间
  → 获取不同类型资源
  → 建立独立证据
  → 发现缺口、冲突和反证
  → 判断搜集充分性
  → 交付报告与可追溯材料
```

二者的核心区别是：

> Research Agent 主要优化答案质量；情报搜集智能体主要优化证据搜集质量和结论可复核性。

### 2.2 总体优化目标

系统最终优化目标可表述为：

> 在给定时间、网络、算力、模型请求、搜索、抓取和下载预算内，最大化关键问题的独立有效证据覆盖，同时保证来源可追溯、过程可解释、结果可验证。

该目标包含五个维度：

| 维度 | 技术含义 | 不应采用的替代指标 |
|---|---|---|
| 覆盖广度 | 核心问题、来源角色、语言、时间和地域得到合理覆盖 | 搜索结果总数 |
| 研究深度 | 能够进入官网栏目、附件、结构化数据和多媒体原件 | URL 跳转深度 |
| 证据质量 | 事实获得精确引文、语义审核和必要的独立来源支持 | 文档归档数量 |
| 调研效率 | 单位 Query、Fetch、Token 和时间产生更多 `full` evidence | 模型调用次数 |
| 可审计性 | 能解释为何搜索、为何采用、为何继续以及为何停止 | 只有最终报告 |

### 2.3 功能目标

系统需要完成以下闭环：

1. 根据主题形成 2—6 个稳定的核心调研问题；
2. 为每个问题形成可执行的搜索和来源计划；
3. 发现搜索引擎、站点、附件和实体关系中的公开资源；
4. 安全获取 HTML、PDF、Office、图片、音频和视频；
5. 将原始材料转化为带定位信息的可搜索正文；
6. 将候选陈述保存为原子事实，并绑定精确引文；
7. 独立审核引文是否真正支撑事实；
8. 判断问题覆盖、来源独立性、时效、冲突和反证；
9. 在充分、无进展或预算耗尽时确定性停止；
10. 输出结构化报告、材料导读和完整来源链。

### 2.4 非功能目标

| 约束领域 | 目标 |
|---|---|
| 部署 | 单机、本地工作区，不依赖 Celery、Redis 或分布式爬虫集群 |
| 模型 | 兼容 OpenAI 风格接口，可接入本地 Qwen 和远程模型服务 |
| 上下文 | 支持 16K、32K、64K、128K、256K 配置档位 |
| 恢复 | 长任务可从持久状态续跑，不依赖完整对话历史 |
| 安全 | 公开页面、SSRF 防护、DNS pinning、逐跳重定向校验、robots 和预算约束 |
| 完整性 | 原件、正文和报告具有 SHA-256 校验及绑定关系 |
| 可解释 | 查询、候选、抓取、证据、覆盖和停止均应可追踪 |
| 可测试 | 确定性逻辑有夹具测试，真实质量通过冻结语料和联网任务验收 |

## 3. 核心设计原则

### 3.1 从答案导向转向证据导向

搜索摘要只能作为候选线索，不能直接进入证据链。正式结论必须满足：

```text
归档原件
  → 提取正文
  → 精确引文定位
  → 事实—证据关系
  → 独立语义审核
  → 覆盖规则通过
  → 进入报告
```

这使系统能够区分“模型看到了某个说法”和“系统已经拥有可发布证据”。

### 3.2 从 Query 驱动转向问题与缺口驱动

Query 是搜索执行手段，不是任务管理单元。真正应控制搜索的是：

- 当前哪个核心问题没有回答；
- 缺少哪类来源；
- 缺少一手材料还是第二独立来源；
- 是否缺少规定时间范围内的材料；
- 是否存在尚未处理的冲突或反证；
- 哪项动作最可能增加有效证据。

因此，目标控制链应为：

```text
Question → Coverage Gap → Search Decision → Query / Source / Site
```

而不是：

```text
Topic → 生成大量 Query → 达到次数后停止
```

### 3.3 Search 与 Fetch 分离

系统将信息发现与资源获取分为两个阶段：

- **Search / Discovery**：判断哪里可能存在有价值的信息；
- **Fetch / Acquisition**：可靠、安全地获取已经发现的资源。

这一区分已经在当前代码中落地：搜索结果仅是候选，只有经过 `fetch.py` 或 `crawl.py` 归档的材料才能被 `evidence.py` 使用。

### 3.4 模型判断与确定性控制分离

模型适合处理语义理解和开放式判断，程序负责可计算、可验证的边界。

| 模型负责 | 确定性程序负责 |
|---|---|
| 理解主题和目标 | ID、状态、阶段和预算 |
| 建议核心问题 | URL 安全、规范化与去重 |
| 根据缺口生成专业 Query | 查询公平性和候选处置状态 |
| 从材料提出事实候选 | 文档哈希和引文定位 |
| 审核语义蕴含 | 来源独立性、时间范围和覆盖计算 |
| 组织报告语言 | Evidence Gain、停止条件和完成状态 |

### 3.5 权威状态与派生视图分离

任务、文档、事实、证据和审核结果是权威数据；覆盖矩阵、候选漏斗和效率指标是可以重建的派生视图。

派生视图不能成为第二套事实源。这样可以避免搜索矩阵显示“已覆盖”，但正式证据状态仍然不足的冲突。

## 5. 当前权威数据模型

| 对象 | 作用 | 权威来源 |

### 5.2 稳定追溯链

当前系统已经支持：

```text
报告结论
  → Fact ID
  → Evidence ID
  → Document ID
  → 原文行号或音视频时间戳
  → 原件 SHA-256 / 正文 SHA-256
```

这一追溯链是后续搜索控制面和可观测性建设不能破坏的底座。

### 5.3 应作为派生数据的对象

以下对象可以缓存，但必须能够由权威状态和 Trace 重建：

- 问题 × 来源证据覆盖矩阵；
- Candidate Ledger；
- 搜索—归档—阅读—证据—事实转化漏斗；
- Evidence Gain；
- 来源传播关系；
- Web 仪表盘统计；
- 实验对比指标。

## 6. 搜索与证据覆盖目标架构

### 6.1 目标控制闭环

```text
用户目标与限制
       │
       ▼
关键问题 + 最低证据要求
       │
       ▼
覆盖矩阵派生视图 ◄────────────────────────────┐
       │                                       │
       ▼                                       │
Gap Detector：未回答/单源/缺一手/缺时效/冲突 │
       │                                       │
       ▼                                       │
Next Action Selector                           │
       │                                       │
       ├── 本地文档补证                        │
       ├── 搜索引擎发现                        │
       ├── 权威来源直取                        │
       ├── Sitemap/RSS/下载中心发现            │
       └── 受控实体扩展                        │
       │                                       │
       ▼                                       │
Candidate Ledger                               │
       │                                       │
       ▼                                       │
Fetch / Crawl / Browser → Extract              │
       │                                       │
       ▼                                       │
Document → Fact → Evidence → Review             │
       │                                       │
       ▼                                       │
Conflict / Coverage / Evidence Gain ────────────┘
       │
       ▼
Stop Decision → Material Digest / Report
```

### 6.2 问题 × 来源证据覆盖矩阵

查询矩阵回答“计划执行哪些 Query”，覆盖矩阵回答“每个问题已经获得什么证据，还缺什么”。两者不能混为一体。

覆盖矩阵按关键问题和来源角色组织：

| 来源角色 | 典型范围 |
|---|---|
| `official` | 企业官网、IR、项目方和机构原始披露 |
| `government` | 政府、监管、司法和公共机构 |
| `news` | 具有独立采编能力的媒体 |
| `academic` | 论文、高校和研究机构 |
| `industry` | 行业协会、咨询和专业资料 |
| `structured` | 数据库、交易所、统计表和公开数据集 |
| `social` | 社区、社交媒体、用户反馈和反证线索 |

每个矩阵格子至少派生：

```text
question_id
source_role
applicability
search_count
candidate_count
archived_document_count
read_document_count
full_evidence_count
independent_source_groups
conflict_count
last_searched_at
evidence_gain
status
```

状态限定为：

```text
not_applicable → planned → searched → candidate_found
→ acquired → evidenced → covered / conflicted
```

第一版应在 `coverage.py` 中作为派生函数实现，不新增第二套权威覆盖状态。

### 6.3 覆盖缺口驱动的下一动作

确定性调度器按以下优先级选择动作：

1. 未回答的核心问题；
2. 已有事实但没有 `full` evidence；
3. 单源事实缺少第二独立来源；
4. 缺少一手或高质量来源；
5. 缺少指定时间范围内材料；
6. 存在未解决冲突或反证；
7. 适用的结构化数据或附件尚未搜索；
8. 一般背景扩展。

动作对象应包含：

```text
question_id
gap_type
action_type
target_source_roles
query_slot
query
language
time_range
reason
```

缺口由程序计算，具体专业 Query 可由模型生成，但必须通过 Pydantic 校验，并受问题公平性、重复查询和总预算约束。

### 6.4 Candidate Ledger

当前跨查询、跨引擎结果缺少统一身份。目标候选台账以 canonical URL 为键，汇总全部发现信号：

```text
canonical_url
question_ids
discovery_queries
query_slots
engines_and_ranks
source_group
source_type
first_seen_at
last_seen_at
fetchable
archived_document_id
decision
decision_reason
```

候选排序第一版使用确定性规则或 Reciprocal Rank Fusion，不训练独立排序模型。排序综合：

- 主题实体最低相关性；
- 查询意图匹配；
- 来源角色；
- 时间范围；
- 新来源组；
- 多引擎共同命中；
- 搜索排名；
- 可抓取性。

每个候选必须有最终处置原因，避免系统只能说明“搜索返回了什么”，却不能说明“为什么抓取或忽略”。

### 6.5 信息空间发现

搜索引擎只负责发现入口。高价值站点还应继续发现：

- `robots.txt` 中声明的 Sitemap；
- Sitemap Index；
- RSS/Atom 和 `<link rel="alternate">`；
- 新闻、公告、下载和文档中心；
- 附件与 `Content-Disposition` 文件名；
- 同源且通过安全校验的公开资源链接。

第一阶段不自动登录、不绕过验证码、不猜测私有 API、不批量扫描子域，也不绕过 robots 或访问控制。

### 6.6 问题感知的抓取调度

当前抓取已支持来源类型和注册域公平轮转。目标调度结构为：

```text
关键问题 → 缺口/来源角色 → 注册域 → URL 优先级
```

`CrawlEntry` 可兼容增加：

```text
question_ids: []
discovery_method: search | direct_source | sitemap | rss | page_link | entity
query_slots: []
target_source_roles: []
```

同时继续保留 canonical URL 去重、域名配额、论坛比例、depth、相关性、附件价值、安全限制和取消恢复语义。

### 6.7 本地材料优先补证

抓取与提取已经付出成本，本地材料应先于新一轮公网泛搜被利用。

实施顺序为：

1. 允许部分高价值关键词命中，并提高标题权重；
2. 根据问题时间范围、来源角色和新来源组过滤或加权；
3. 对单源事实提取主体、动作、数字和时间进行补证检索；
4. 对冲突分别检索双方口径；
5. 固定基准证明词法召回不足后，再引入 SQLite FTS5/BM25；
6. 向量检索只作为可重建候选重排，不作为正文权威存储。

### 6.8 Evidence Gain 与停止判断

每个研究动作完成后分别统计：

```text
新增 full evidence
新增独立来源组
新覆盖矩阵格子
新发现的重要冲突或反证
```

第一版不必将这些分项压缩成主观总分。

满足以下任一条件可以停止：

1. 所有核心问题达到充分性要求；
2. 连续两轮定向动作没有新增证据、来源组或覆盖格子；
3. 每个剩余缺口均执行过适用来源和时间范围搜索但无候选；
4. 搜索或抓取预算耗尽；
5. 网络、处理器或公开数据条件使剩余缺口不可完成。

停止必须同时记录剩余缺口、已尝试动作和 `sufficient` 或 `with_gaps` 状态。发现新冲突属于有效信息增益，即使其使 `gap_score` 上升。

## 7. 获取、解析与多媒体技术方法

### 7.1 安全获取链

资源获取继续复用现有安全链：

```text
URL canonicalization
  → scheme/host 检查
  → 公网 DNS 解析
  → DNS pinning
  → HTTP 请求
  → 重定向逐跳重新验证
  → Content-Type / 大小检查
  → 原件归档与哈希
```

递归采集继续遵守 robots、单域限速、并发和总下载预算。自动递归路径不能使用削弱 DNS pinning 的不安全回退。

### 7.2 动态网页

当静态 HTML 被判定为无有效正文的 JavaScript 壳时，可选的 `BrowserRenderer` 使用 Chromium 执行页面脚本。渲染结果继续经过正文提取、链接发现、原文与 DOM 双哈希和证据审核。

浏览器能力受以下边界约束：

- 仅在静态路径不足时启用；
- 单页渲染超时；
- 请求数量和下载字节限制；
- 浏览器并发限制；
- 公网 URL 验证或生产隔离网络声明；
- 取消任务时终止渲染子进程。

### 7.3 多媒体资源

| 资源类型 | 当前处理路径 | 降级方式 |
|---|---|---|
| HTML/TXT/CSV | 文本、日期和链接提取 | 记录失败原因 |
| PDF | PyMuPDF 文本；无有效文本时 OCR | 保留原件，标记 unavailable/failed |
| DOCX/XLSX/PPTX | 对应 Python 库解析文本和链接 | 保留原件 |
| 旧式 Office | LibreOffice headless 转换 | 处理器缺失则 unavailable |
| PNG/JPEG/WebP/TIFF | Pillow 校验 + Tesseract OCR | 低质量文本不得作证据 |
| MP3/WAV/M4A/OGG/FLAC | FFmpeg + faster-whisper | 转写失败保留原件 |
| MP4/WebM/MOV | FFmpeg 提取音轨后转写 | 超时或模型缺失标记 unavailable |

资源类型分派当前由 `extract_resource()` 统一完成。现阶段没有必要为单个实现建设复杂插件框架。

## 8. 证据、冲突和报告方法

### 8.1 原子事实

事实必须能够单独验证。多个时间、主体、数字或因果结论不应被无边界合并为一个声明，否则一条引文只能部分支撑整个事实。

系统使用稳定 Fact ID，并通过 `supersede_fact()` 维护无环替换链，使错误或过时事实可以被明确替代而非静默覆盖。

### 8.2 精确引文

`EvidenceSupport` 必须引用已成功提取的文档正文。引文经过规范化后仍需逐字存在，并记录起止行号；音视频正文保留时间戳，从而能够定位到原始片段。

### 8.3 隔离语义审核

独立审核 Agent 将事实和候选引文判定为：

- `full`：引文完整支撑事实；
- `partial`：仅支撑事实的一部分；
- `irrelevant`：没有直接支撑关系；
- `contradicts`：与事实矛盾。

只有 `full` 计入正式覆盖。该门槛避免主 Agent 因为已经投入搜索成本而放宽自己的证据判断。

### 8.4 声明类型与独立来源

系统根据声明性质应用不同规则：

- 一手原始披露可由匹配的一手来源支持；
- 带明确来源归属的单方陈述可以保留为 reported；
- 重大数字、争议性事实和 corroborated 声明要求多个独立来源组；
- inference 必须绑定已经满足各自证据规则的事实。

网页数量不能代替独立来源数量。目标系统还需识别 `original`、`repost`、`quoted`、`near_duplicate` 和 `unknown` 传播关系。

### 8.5 报告完整性

正式报告只能引用当前 coverage fingerprint 下仍有效的事实。报告生成后绑定：

- 最新覆盖指纹；
- 报告文件哈希；
- 被引用文档的哈希。

证据、冲突、文档或报告发生变化后，完成门禁会拒绝把过期产物标记为最终结果。

当模型无法生成合法报告草稿时，系统可从持久状态确定性构建安全草稿，只纳入具有 `full` 支撑的事实，并为未回答问题保留空章节和局限说明。

## 9. 上下文与本地模型架构

### 9.1 上下文不是权威存储

长任务不能依赖把所有网页和历史工具结果持续放入模型窗口。当前系统将以下状态持久化：

- 任务与问题；
- 归档文档；
- 已读状态和阶段快照；
- 事实与证据；
- 审核与覆盖；
- 报告和停止原因。

对话历史被裁剪后，`context.py` 从这些状态生成紧凑快照，告诉模型当前阶段和唯一下一动作。

### 9.2 可配置窗口

系统支持 16K、32K、64K、128K 和 256K 上下文档位，并由窗口大小派生历史字节与单工具结果限制。配置必须匹配模型服务实际声明，不能把客户端配置得比服务窗口更大。

### 9.3 小模型适配原则

本地小模型的可靠性主要来自：

- 缩小每次决策范围；
- 为当前阶段给出唯一动作；
- 将复杂对象兼容问题留在严格 Pydantic 校验边界处理；
- 自动续跑但共享任务级累计预算；
- 失败后从本地状态恢复，不重复搜索和归档；
- 最终完成摘要由持久状态生成，而非使用模型自由文本。

扩大上下文和输出 Token 只能缓解容量问题，不能替代状态机、搜索控制面和证据门控。


CLI trace、Web SSE 和实验分析应是同一事件流的不同投影，而不是三套独立语义。

- 任务可以从搜索走到正式报告；
- 垃圾链接和来源洪泛可以被确定性规则显著抑制；
- 双源门控、时效和证据审核能够改变最终覆盖结果；
- PDF、图片和视频处理链能够在固定目标上工作；
- 受限上下文模型可以通过持久状态完成中断恢复；
- 模型夸大的自由文本不会污染正式报告。

已有实验尚不能证明：

- 任意主题都能稳定达到 100% 关键数字双源率；
- 搜索结果对每个问题都具备稳定的 Precision@10 与 Recall@50；
- 站点地图、RSS 和下载中心发现已经形成规模化收益；
- 动态实体和问题扩展能够在预算内稳定收敛；
- 多媒体格式支持等同于任意真实任务中的高召回率。

## 14. 分阶段技术路线

### 14.1 阶段 A：证据覆盖控制面

按以下顺序建设：

1. 覆盖矩阵派生视图；
2. 缺口到下一动作的确定性映射；
3. 问题公平调度以及语言、时间透传；
4. Candidate Ledger 与统一 URL 去重；
5. 增量统一 Trace；
6. Evidence Gain 和停止原因。

完成后系统必须能够回答：

> 当前缺什么，为什么执行这个动作，动作产生了什么，覆盖如何变化，为什么继续或停止。

### 14.2 阶段 B：信息空间发现与转化效率

1. Sitemap、RSS、下载中心和附件入口发现；
2. 问题感知的抓取调度；
3. 本地材料补证排序；
4. 近重复和来源传播关系；
5. 多媒体专项数据集复测；
6. Web 覆盖矩阵和转化漏斗。

阶段 B 不扩大总预算，主要观察有效来源、文档利用率、双源率和单位资源的 `full` evidence 产出。

### 14.3 阶段 C：受控自适应与数据闭环

1. 实体扩展建议；
2. Question Proposal；
3. 教师模型与本地模型轨迹对比；
4. 策略错误归因；
5. Benchmark 和蒸馏数据集。

阶段 A、B 的状态、指标和停止条件未稳定前，不应开放自动无限实体或问题扩展。

## 15. 量化验收标准

### 15.1 状态与可追溯性

| 指标 | 目标 |
|---|---:|
| Query 绑定 `question_id` | 100% |
| Query 绑定 `gap_type` 和决策原因 | 100% |
| 候选 URL 有最终处置原因 | 100% |
| 文档可追溯到发现动作 | 100% |
| Evidence 可追溯到文档和行号/时间戳 | 100% |
| Coverage 可追溯到 `full` review | 100% |
| 异常退出后已完成事件保留率 | 100% |
| 派生矩阵与权威状态一致 | 100% |

### 15.2 搜索质量

| 指标 | 目标 |
|---|---:|
| Precision@10 | ≥70% |
| 必找来源 Recall@50 | ≥80% |
| 适用任务 Authoritative@10 | ≥40% |
| 时间约束任务 InScope@10 | ≥70% |
| 跨查询 canonical URL 重复率 | ≤5% |
| 无关年份/日历污染进入抓取队列 | 0 |

### 15.3 来源与证据覆盖

| 指标 | 目标 |
|---|---:|
| 每个核心问题一手候选 | ≥1 |
| 每个核心问题独立验证候选 | ≥2 个来源组 |
| 最大非一手域占比 | ≤15% |
| 前两域占比 | ≤35% |
| 有效域数量 | ≥6 |
| 社交/论坛占比 | ≤10% |
| 近重复材料占比 | ≤10% |
| 关键数字双源验证率 | 100% |
| 报告无证据事实 | 0 |

### 15.4 转化与资源效率

| 指标 | 目标 |
|---|---:|
| 文档证据利用率 | ≥20% |
| 已读文档形成 evidence 比例 | 相对基线提高 ≥30% |
| `full evidence / Search Query` | 相对基线提高 ≥30% |
| `full evidence / Fetch` | 相对基线提高 ≥30% |
| `Token / full evidence` | 相同模型和任务下降 ≥20% |
| 连续两轮零 Evidence Gain 后继续泛搜 | 0 次 |

所有指标必须定义分子、分母和不可计算条件。不得通过减少问题、放宽证据标准或删除失败样本达到阈值。

## 16. 测试与评测方法

### 16.1 确定性测试

使用固定夹具验证：

- 覆盖矩阵计算；
- 问题和来源公平调度；
- URL canonicalization 和候选融合；
- Sitemap、RSS 和附件发现；
- 来源传播关系；
- Evidence Gain；
- Trace 异常恢复；
- 停止条件与 `with_gaps` 出口。

### 16.2 冻结公开语料

用于稳定测量：

- Precision@10；
- 必找来源 Recall@50；
- 本地文档检索召回；
- 独立来源识别；
- 关键事实双源率；
- 报告与证据一致性。

### 16.3 真实联网任务

真实验收至少覆盖：

1. 企业发展与商业化；
2. 政策与监管；
3. 投融资与财务数据；
4. 技术路线与学术研究；
5. 重大事件与争议；
6. 动态网页与多媒体专项。

每个任务提前定义必找来源、必须回答维度、已知冲突和适用格式。普通质量实验与多媒体专项不能继续依赖同一个无法命中全部目标格式的主题。

## 17. 安全、合规与工程边界

### 17.1 必须保留的安全边界

- 仅采集无需登录的公开 HTTP/HTTPS 内容；
- 遵守 robots.txt；
- 保持 DNS pinning、逐跳重定向验证和 SSRF 防护；
- 浏览器仅在静态抓取不足时启用；
- 浏览器和抓取均受并发、请求、时间和字节预算限制；
- 不自动绕过验证码、登录、付费墙或访问控制；
- 不执行网页中的指令和提示注入内容；
- 拒绝脚本、可执行文件、压缩包和不支持类型；
- 处理器缺失时原件保留，但不进入证据；
- 对外下载执行哈希检查、attachment 和 `nosniff`。

### 17.2 当前明确不做

- 不引入 Celery、Redis 或 Scrapy；
- 不建设独立图数据库；
- 不为单个实现建设 Fetcher/Parser 插件框架；
- 不为排序提前训练独立模型；
- 不在没有基准缺口前引入向量数据库；
- 不自动无限扩展实体和问题；
- 不用增加抓取数量掩盖搜索质量问题；
- 不用更长提示词替代确定性状态和门控；
- 不用文档数、`stage=done` 或 `gap_score=0` 单独证明成功。

## 18. 技术风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 搜索引擎结果波动 | 指标难复现 | 冻结语料 + 真实联网双轨评测 |
| 单源信息客观稀缺 | 双源率无法达到 100% | 保留 reported/with_gaps，披露已尝试来源 |
| 本地模型工具调用不稳定 | 任务循环或参数校验失败 | 严格 Schema、兼容解析、唯一动作和累计预算 |
| 小上下文导致历史丢失 | 重复搜索或阶段回退 | 持久状态快照和幂等工具 |
| 多媒体处理耗时 | 队列阻塞和预算失控 | 独立子进程、超时、取消和质量门控 |
| 动态网页扩大攻击面 | SSRF、资源消耗和注入 | 隔离浏览器、URL 校验、请求与字节限制 |
| 覆盖矩阵成为第二状态源 | 结果相互矛盾 | 只做派生视图，可由 evidence/coverage 重建 |
| 过强门控导致无法完成 | 任务死锁 | 预算耗尽和 no-progress 的诚实出口 |

## 19. 最终结论

当前情报搜集智能体已经完成从“模型联网回答”向“本地证据生产系统”的关键转变。搜索结果必须经过安全归档、内容提取、精确引文、独立审核和覆盖判断，才能成为正式报告结论；任务能够中断恢复，并在证据不足时以 `with_gaps` 诚实交付。

真实实验说明，系统已经基本解决以下问题：

- 能否完成端到端公开信息调研；
- 能否抑制垃圾链接和来源洪泛；
- 能否对重大事实执行来源门控；
- 能否处理 PDF、图片和视频等材料；
- 能否在受限上下文和本地模型条件下恢复任务；
- 能否防止模型夸大污染正式报告。

下一阶段要解决的不是“让 Agent 搜索更多”，而是建立确定性搜索控制面，使每一次查询、抓取和阅读都对应明确问题与证据缺口，并能够计算其实际证据收益。

技术优先级应保持为：

```text
权威证据状态
  > 覆盖矩阵与缺口
  > 搜索决策与候选治理
  > 站点和资源发现
  > Evidence Gain 与统一 Trace
  > 受控实体和问题扩展
  > 更大预算和更复杂基础设施
```

按照该路线推进，项目能够逐步形成一个适合本地部署、可量化验收、可持续优化，并明显区别于通用云端 Research Agent 的专用情报调研系统。

## 附录 B：指标口径

```text
文档证据利用率
  = 被至少一条 Evidence 引用的独立文档数 / 成功归档文档数

关键数字双源验证率
  = 获得至少两个独立来源组 full 支撑的关键数字事实数
    / 所有进入报告候选的关键数字事实数

有效域数量
  = 1 / Σ(各注册域文档占比²)

full evidence / Search Query
  = 新增 full evidence 数 / 实际搜索 Query 数

Evidence Gain
  = 新增 full evidence、独立来源组、覆盖格子和重要冲突的分项增量
```
