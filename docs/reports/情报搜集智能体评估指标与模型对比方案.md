# 情报搜集智能体评估指标与模型对比方案

## 1. 目的

本文定义一套可重复、可审计、可量化的评测方法，用于：

1. 衡量情报搜集智能体在真实公开信息调研中的效果；
2. 公平比较云端大模型和本地小模型；
3. 判断本地模型是否达到可替代门槛；
4. 评价蒸馏、微调、上下文管理和工具调用优化是否真实有效；
5. 将质量问题定位到检索、证据、报告或运行阶段，而不是只看最终文笔。

本方案不使用单一“准确率”。系统采用“硬门槛、核心质量分、效率指标”三层结构：硬门槛不可由其他分数补偿，效率不进入质量总分。

## 2. 评测对象与边界

一次完整评测覆盖以下链路：

```text
任务理解 → 检索规划 → 搜索发现 → 网页/多媒体采集
        → 内容理解 → 事实与证据 → 覆盖判断 → 报告生成
        → 运行稳定性、时间、Token、算力和成本
```

需要区分两种能力：

- **受控模型能力**：给定相同冻结材料，只比较阅读、证据、上下文和报告能力。
- **端到端Agent能力**：模型自行调用搜索和采集工具，评价真实互联网调研结果。

实时互联网结果会变化，因此不能只用端到端运行判断模型本身。两种实验必须分别报告。

## 3. 评分结构

核心质量分为100分：

\[
Q = 25\%问题覆盖 + 25\%证据质量 + 20\%搜索质量
  + 20\%报告质量 + 10\%运行稳健性
\]

每个输入指标先归一化到 `0—1`，再按 `experiments/evaluation/policy.yaml` 加权。评分器输出小数保留四位，展示时可保留两位。

### 3.1 硬门槛

| 门槛 | 默认阈值 | 数据来源 |
| --- | ---: | --- |
| 任务有效完成 | 100% | manifest、task终态和报告 |
| 无依据的重要结论数 | 0 | 人工核查报告中的重要结论 |
| 结论到材料的可追溯率 | 100% | 报告、证据和文档台账 |
| 关键数字双独立来源率 | 100% | 事实与来源组复核 |
| 工具调用参数合法率 | ≥99% | trace与工具错误 |
| 上下文溢出数 | 0 | run.log与模型错误 |
| 严重安全事件数 | 0 | 安全日志和任务状态 |
| 报告结构合法 | 100% | 报告解析或人工确认 |

只要一项失败，该次运行的 `valid_run=false`。质量分仍保留用于诊断，但不得计作有效交付。

### 3.2 指标评分表

| 组 | 指标 | 标准化计算口径 | 主要证据 |
| --- | --- | --- | --- |
| 问题覆盖 | `core_question_coverage` | 按问题权重计算；covered=1、partial=0.5、gap=0 | 问题清单、覆盖快照、人工复核 |
| 问题覆盖 | `key_fact_recall` | 找到的关键事实权重÷金标准关键事实权重 | benchmark、facts、报告 |
| 证据 | `claim_support_rate` | 有有效证据的重要事实÷全部重要事实 | 报告事实抽检 |
| 证据 | `citation_precision` | 引用确实支持对应结论数÷抽查引用数 | 引文与归档原文 |
| 证据 | `independent_verification_rate` | 达到要求来源组数的关键事实÷需交叉验证事实 | facts、evidence、source groups |
| 证据 | `key_numeric_double_source_rate` | 两个独立来源支持的关键数字÷全部关键数字 | 数字事实复核表 |
| 证据 | `conflict_handling_rate` | 已发现且正确处理的已知冲突÷金标准冲突 | conflicts、报告限制说明 |
| 搜索 | `precision_at_10` | 每个问题前10项中相关结果÷已检查结果 | 搜索结果人工标注 |
| 搜索 | `must_find_recall_at_50` | 前50项找到的必查来源÷必查来源总数 | benchmark、搜索轨迹 |
| 搜索 | `source_role_coverage` | 已覆盖必要来源角色÷要求角色 | 来源目录 |
| 搜索 | `source_diversity` | `min(有效域名数÷6, 1)` | ANALYSIS、来源域名 |
| 搜索 | `duplicate_control` | 重复率≤10%记1；超过后按剩余区间线性降至0 | canonical URL、近重复检测 |
| 报告 | `factual_accuracy` | 正确事实权重÷抽查事实权重 | 人工事实复核 |
| 报告 | `answer_completeness` | 已充分回答问题权重÷全部问题权重 | 问题与报告章节 |
| 报告 | `evidence_alignment` | 结论强度与证据一致数÷抽查结论数 | 结论—证据配对 |
| 报告 | `expert_usefulness` | 盲评1—5分除以5 | 专家评分表 |
| 稳健性 | `valid_completion` | 有效报告=1，否则0 | manifest、task、output |
| 稳健性 | `tool_call_validity` | 合法工具调用÷全部工具调用 | trace、错误日志 |
| 稳健性 | `stage_progress` | 完成的必需阶段÷全部必需阶段 | task stage、state |
| 稳健性 | `loop_control` | `1-无进展重复调用数÷全部调用数` | ANALYSIS重复调用 |
| 稳健性 | `context_stability` | 无上下文溢出=1，有溢出=0 | run.log、模型服务日志 |

没有适用冲突时，`conflict_handling_rate` 记1，并在 `note` 中写明“本题无预置冲突”，不能留空或猜测。所有指标必须附 `evidence`；大模型自动评分只能作为辅助，不得替代关键事实和引文的人工抽检。

## 4. 资源与效率指标

效率与质量分分开呈现：

| 字段 | 单位 | 口径 |
| --- | --- | --- |
| `elapsed_seconds` | 秒 | 从任务开始到终态的墙钟时间 |
| `input_tokens`、`output_tokens` | Token | 本任务独占统计，服务全局累计值不可直接使用 |
| `model_requests` | 次 | 模型请求总数 |
| `tool_calls` | 次 | Agent工具调用总数 |
| `monetary_cost` | 元 | 云端账单；本地为电费和硬件折旧的统一核算值 |
| `gpu_seconds` | GPU秒 | 本任务占用模型设备的时间 |
| `energy_kwh` | 千瓦时 | 可测时记录，缺失填 `null` |

主要管理指标为“每份有效报告成本”：

\[
有效报告成本 = 总运行成本 ÷ 通过全部硬门槛的报告数
\]

本地双槽模型还应在实验报告中记录单槽首Token延迟、双路合计解码速度、槽位利用率和每小时有效报告数。这些属于部署性能，不直接进入报告质量分。

## 5. 云端与本地模型对比协议

### 5.1 控制变量

同一批对比必须固定：

- 代码提交、系统提示和工具定义；
- benchmark版本和问题文本；
- 搜索服务、地域、运行时间窗口；
- `max_turns=200`、抓取深度、URL与字节预算；
- 温度、思考模式、上下文窗口和输出上限，并在结果中明确记录差异；
- 媒体处理器版本和可用状态。

每个模型每个任务至少重复3次。正式版本建议包含30个任务，每类不少于6个；发布验收扩展到60个任务。报告中同时给出平均值、中位数、p95和最差10%任务，不能只展示最佳运行。

### 5.2 三类实验

1. **冻结材料实验**：所有模型读取完全相同的归档材料，隔离模型理解与报告能力。
2. **实时端到端实验**：模型自主搜索、采集、核验和生成报告，评价整体Agent能力。
3. **故障实验**：注入超时、429、空搜索、坏PDF、处理器缺失、上下文临界和中断恢复。

### 5.3 配对原则

模型比较只能使用双方都完成的相同 `case_id`。评分器输出 `paired_cases`，缺少资源成本时选型状态为 `incomplete`。禁止用不同题目、不同搜索时段或不同预算的结果直接计算替代率。

## 6. 本地小模型选型门槛

\[
质量保持率 = 本地模型配对任务质量分之和 ÷ 云端模型配对任务质量分之和
\]

默认推荐条件：

- 所有关键硬门槛按运行检查；
- 有效运行率≥90%；
- 总体质量保持率≥90%；
- 任一分类质量保持率≥85%；
- 单份有效报告成本相对云端降低≥30%。

满足条件输出 `recommended`；数据缺失输出 `incomplete`；其余输出 `not_recommended`。选型结论必须同时展示质量、有效运行率和成本，不能把本地数据不出域等特殊价值折算成虚假的质量分。

## 7. 蒸馏与微调评测

教师模型不是金标准。教师、学生和微调前基线必须面对同一人工标注任务集。

必须报告：

- 学生相对教师的核心质量保持率；
- 学生相对微调前模型的金标准提升率；
- 关键事实与证据集合召回率；
- 工具参数合法率和阶段推进成功率；
- 搜索意图、补证和停止决策正确率；
- 教师错误继承率；
- 回归任务比例；
- 同等质量下Token、耗时和成本降低率。

工具动作一致率只用于诊断。不同搜索路径可能得到同等甚至更好的证据，不能要求学生机械复制教师轨迹。

## 8. 数据格式

### 8.1 Benchmark

`benchmark.example.json`包含：

- `benchmark_id`与版本；
- 分类、主题、问题及权重；
- 必查来源；
- 关键事实、所属问题和独立来源要求；
- 已知冲突；
- 必须覆盖的材料类型。

基准一旦开始正式对比不得原地改写。题目或金标准变化时创建新版本，并保留旧版结果。

### 8.2 Evaluation input

一次运行一份JSON，包含：

- benchmark、case、run和模型身份；
- 归一化指标及证据位置；
- 硬门槛原始值及证据位置；
- 时间、Token、请求、工具、成本和算力数据；
- 审核人和时间。

示例文件中的数字仅用于验证评分程序，不属于真实实验结果。

## 9. 人工审核规范

1. 审核者不知道报告由哪个模型生成；
2. 核心问题、关键数字、关键结论和疑似冲突全部审核；
3. 其他事实与引用随机抽查至少20条，不足20条时全部审核；
4. 搜索质量按每个问题Top10和整体Top50标注；
5. 两名审核者分歧超过10个百分点时，由第三人裁决；
6. 审核结论必须留下证据定位和简短理由；
7. 禁止在看到模型名称后调整事实正确性标准。

## 10. 执行流程

```text
冻结benchmark与policy
  → 为各模型生成相同运行命令
  → 每题重复运行并保留全部产物
  → analyze_run生成自动指标
  → 盲审并填写evaluation JSON
  → score生成单次质量与门槛结果
  → compare生成配对模型对比
  → 记录结论、失败任务和下一轮假设
```

具体命令见 `experiments/evaluation/README.md`。正式结果必须保留原始运行目录、评分输入、评分输出和审核记录，确保结论可重新计算。
