# 情报调研智能体后续建设与量化验收方案

## 1. 文档目的

本文档用于指导情报调研智能体未来六个月的建设、试验、试运行和验收，同时作为甲方项目管理与乙方研发执行的共同基线。

本期采取“快速形成核心成果、集中补齐一期功能、系统测试完善、真实业务试运行”的推进方式：

1. 前两周完成最重要的效果能力，用真实专题和真实数据证明系统价值。
2. 随后一个月补齐一期范围内的全部功能并完成端到端联调。
3. 再用一个月完成10个真实专题验收、专项测试和缺陷收敛。
4. 后续三个半月由一名业务用户在单机本地环境试运行，按月度数据复验效果。

本文所称“全部功能”特指本文件第6章定义的一期交付范围，不包含多租户、高可用集群、分布式任务队列、复杂RBAC、内网知识库和企业级审批流。这些能力只有在试运行数据证明存在真实需求后才进入下一期。

## 2. 项目现状与建设基础

### 2.1 当前已具备的能力

当前系统已经形成完整的公开信息调研主链路：

- Agent根据主题和用户问题制定调研计划，并自主选择搜索、抓取、阅读、事实保存、证据审核和报告生成工具。
- 支持公开搜索、定向抓取、持久化深度采集、URL去重、缓存、断点恢复、robots.txt、域名限速和下载预算。
- 支持静态网页和JavaScript动态页面；浏览器路径执行公网地址校验、请求限制、字节计量和沙箱失败关闭。
- 支持PDF、Office、TXT、CSV、图片OCR、音频转写和视频音轨转写；处理器缺失时保留原件但禁止作为文本证据。
- 事实必须绑定归档原文、精确引文和行号或时间戳，并经过独立语义审核。
- 支持来源冲突、问题覆盖度、信息缺口、正式调研报告、材料摘要和1—5星阅读推荐。
- 提供本地FastAPI接口、React工作台、SSE进度、任务取消和安全下载。

截至2026年8月17日的最近一次开发验证结果为：后端303项测试通过、1项真实Chromium测试因当前宿主不支持sandbox而跳过；Ruff、Pyright、Python构建，以及前端18项测试、类型检查和生产构建通过。该结果证明代码基线可继续迭代，但不等同于真实专题业务验收。

### 2.2 已有真实实验数据

现有迭代实验已经证明系统能够形成报告和证据，也暴露了影响规模化使用的主要问题。

| 实验 | 耗时 | 模型请求 | 事实/证据 | 覆盖结果 | 主要结论 |
| --- | ---: | ---: | ---: | --- | --- |
| 007 | 20分钟 | 58 | 3/4 | gap=7 | 流程首次完整走完，但图片处理依赖缺失，材料质量不足 |
| 008 | 9.3分钟 | 57 | 15/18 | sufficient，gap=0 | OCR和图片门槛生效，事实与证据显著增加 |
| 009 | 24分钟 | 96 | 16/18 | sufficient，gap=0 | 视频页污染显著下降，但44份材料中仍有28份低相关导航页 |

上述数据说明：

- 证据链、归档、哈希和报告主流程已经可用。
- 环境依赖和采集相关性会直接改变最终结果，必须纳入验收前置条件。
- 当前最大质量瓶颈是深层链接相关性、搜索预算分配、交叉验证和多媒体内容质量，而不是是否能够生成自然语言报告。
- `coverage=sufficient`只能作为系统状态，最终验收仍需人工抽样核查事实与引文，不能单独作为项目通过依据。

### 2.3 当前优先缺口

结合实验记录和现有实现，本期优先处理以下问题：

1. 深度大于等于1的低相关链接仍可能占满采集队列。
2. 搜索预算没有充分随核心问题数量变化，复杂专题容易过早耗尽。
3. OCR需要提升中文字库质量，并区分文字型图片和纯照片。
4. 新闻检索时效、单源重要数据交叉验证和矛盾证据处理仍需真实场景验证。
5. 动态页面能力需要在支持Chromium sandbox的验收环境中完成真实站点验证。
6. 报告生成、覆盖评估等工具仍需减少无进展重复调用。
7. 生产部署的环境检查、运行监控、备份恢复和操作规范需要形成标准交付物。
8. 本地Qwen双槽位调度、长上下文预算和吞吐指标尚未纳入当前验收基线。

## 3. 总体目标与范围

### 3.1 六个月总体目标

在24周内交付一套可在甲方单台工作站本地部署、供一名业务用户使用的公开信息调研智能体，并以10个真实专题证明以下价值：

- 能够从公开互联网发现并归档与主题相关的网页和多媒体材料。
- 能够将材料转化为可检索正文、原子事实、精确引文和结构化报告。
- 能够明确披露单方来源、冲突、信息缺口和处理失败，不伪造来源。
- 能够减少人工搜索、筛选和形成初稿的时间，同时保留人工最终判断权。
- 所有任务状态、原始材料、证据和报告保存在甲方指定环境中，可复核、可恢复、可审计。

### 3.2 一期交付边界

一期包含：

- 单机本地部署和单工作区数据存储。
- 主题调研、可选核心问题和范围约束。
- 多搜索源、静态网页、动态网页和深度采集。
- PDF、Office、图片、音频和视频内容提取。
- 事实、证据、语义审核、冲突、覆盖度和信息缺口管理。
- 结构化调研报告、材料摘要、阅读推荐和来源目录。
- 本地Web工作台、API、SSE进度、取消、恢复、下载和系统状态。
- 运行配置、环境检查、日志、备份恢复说明和验收工具。

一期不包含：

- 登录网站、付费墙或交互式验证码绕过。
- 住宅代理、代理池轮换、stealth指纹伪装等主动反爬规避。
- 多租户、复杂角色权限、跨部门数据隔离和统一身份认证。
- 高可用集群、分布式队列、对象存储和关系数据库改造。
- 自动替代专业人员作出法律、投资、合规或对外发布决定。

### 3.3 单机模型部署基线

一期验收固定使用甲方单机本地模型环境，不以云端模型结果替代本地模型验收。

| 项目 | 一期基线 |
| --- | --- |
| 部署形态 | 单台工作站、单工作区、单业务用户 |
| 模型 | 本地Qwen3.6 27B，通过OpenAI兼容接口调用 |
| 推理槽位 | 2路并行，每路最大256K上下文 |
| 解码吞吐 | 双路合计平均约50 token/s，以部署机实测为准 |
| 任务并发 | 同时只运行1个调研任务；后续任务排队，不并行修改两个任务状态 |
| 模型复用 | 主Agent、证据审核、材料评价和报告生成共用同一模型服务，不重复加载27B模型 |

每路虽支持256K上下文，但不将全部归档原文一次性填入提示词。常规规划、工具选择和证据审核的输入不超过64K，综合报告输入不超过128K；单请求输入硬上限为224K，至少保留32K上下文余量。常规单次输出上限4K，最终报告单次输出上限12K。

### 3.4 支持文件格式与默认上限

下表为一期默认验收边界，MiB按`1024 × 1024`字节计算。单件大小与内部复杂度须同时满足，因此处于字节上限内不等于一定能完成内容提取。

| 材料类型 | 支持格式 | 单件下载上限 | 内部处理上限 | 输出 |
| --- | --- | ---: | --- | --- |
| 静态网页 | HTML、HTM、XHTML | 5 MiB | 重定向逐跳校验 | 正文、行号和链接 |
| 动态网页 | JavaScript渲染HTML | 单页全部请求20 MiB | 最多40个请求，渲染超时15秒 | 原始HTML、渲染DOM和正文 |
| PDF | PDF | 50 MiB | 最多200页；单页栅格不超过25MP，总栅格不超过100MP | 文本或OCR正文、行号 |
| Word | DOC、DOCX | 50 MiB | OOXML最多1024个内部成员且解压后不超过32 MiB | 正文、行号和链接 |
| 表格 | XLS、XLSX | 50 MiB | 最多100个工作表、合计25万单元格；OOXML同上 | 按工作表展开的文本 |
| 演示文稿 | PPT、PPTX | 50 MiB | 最多500页；OOXML同上 | 按页展开的文本 |
| 纯文本 | TXT、CSV | 50 MiB | 按字符编码解码，不执行公式或脚本 | 正文和行号 |
| 图片 | PNG、JPEG/JPG、WebP、TIFF/TIF | 50 MiB | 最多4000万像素 | OCR正文；纯照片标记跳过 |
| 音频 | MP3、WAV、M4A、OGG、FLAC | 50 MiB | 时长不超过30分钟 | 带时间戳的转写文本 |
| 视频 | MP4、WebM、MOV | 50 MiB | 时长不超过20分钟 | 提取音轨后输出带时间戳的转写文本 |

旧式DOC、XLS和PPT依赖LibreOffice headless转换；图片和扫描PDF依赖Pillow、Tesseract及中英文字库；音视频依赖FFmpeg和faster-whisper。处理器缺失时保留已完整下载的原件并标记`unavailable`，不得产生正式证据。

单件超过50 MiB时应立即停止下载，记录`skipped_limit`，已下载字节仍计入任务预算，且不得将不完整文件作为证据。字节数未超限但页数、像素、表格单元格、幻灯片或时长超限时，完整原件仍归档，内容提取标记`skipped_limit`。单任务硬上限为200个URL、深度2和1 GiB实际下载字节。

压缩包、可执行文件、脚本、安装包、磁盘镜像和SVG不在一期支持范围，不尝试解压或执行。

### 3.5 单机并发与资源调度

单机并发的目标是隐藏网络等待、使用两个模型槽位，而不是同时启动多个调研任务。默认限制如下：

| 资源层 | 并发上限 | 调度规则 |
| --- | ---: | --- |
| 活跃调研任务 | 1 | 只有一个任务可修改Agent状态，其余任务FIFO排队 |
| 模型推理 | 2 | 主Agent调用优先；证据审核、材料评价和摘要最多占用1个辅助槽位 |
| Agent状态变更 | 1 | 计划、阶段转换、覆盖结论和报告定稿使用串行状态锁 |
| HTTP抓取 | 全局4 | 单域名最多1，同域请求启动间隔至少1秒 |
| Chromium渲染 | 1 | 每次一个隔离context，关闭弹窗、WebSocket和非必要请求 |
| 轻量文本提取 | 2 | HTML、TXT、CSV和已有文本层的PDF可并行 |
| 重型媒体处理 | 1 | OCR、LibreOffice、扫描PDF和音视频转写串行 |
| 任务状态落盘 | 1 | 原子写入，禁止多进程同时改写同一JSON |

默认将Tesseract、LibreOffice和媒体预处理放在CPU侧。如faster-whisper使用与Qwen相同的加速器，必须先排空两个Qwen槽位再独占执行，不允许与模型推理抢占显存。

当前抓取实现的总字节预算锁覆盖完整下载过程，会使配置中的全局并发4在实际下载时退化为串行。一期应改为“下载前预留额度、结束后按实际字节结算”，同时保证失败和取消时已下载字节仍被计费。未完成该整改前，不得声称网络抓取已达到4路并发。

## 5. 第一阶段：两周形成核心效果

### 5.1 阶段目标

两周内不追求平台化功能，优先证明四件事：

1. 系统能围绕真实问题找到有价值的信息，而不是只返回搜索链接。
2. 报告中的关键结论能够回到归档原文和精确引文。
3. PDF、Office、图片或动态网页中的重要内容能够进入统一报告。
4. 与纯人工流程相比，系统能够明显缩短搜索、材料筛选和报告初稿时间。

### 5.2 三个演示专题

首轮固定使用以下三类真实专题，具体主题由甲方在启动日从实际业务中选定：

| 专题类型 | 必须包含的材料 | 重点验证能力 |
| --- | --- | --- |
| 政策与标准专题 | 政府网页、政策PDF、附件或表格 | 一手来源、发布时间、政策条款引用、信息缺口 |
| 企业与经营专题 | 企业官网/IR、财报、新闻和至少两个独立来源组 | 重要数字、单方陈述标识、交叉验证、动态网页 |
| 行业或事件专题 | 新闻、研究材料、图片或音视频至少一种 | 多源检索、时间线、冲突处理、多媒体提取 |

每个专题设置2—4个核心问题。启动前冻结问题、时间范围、地区、语言和最低来源要求；运行期间不得为了提高分数而修改题目。

### 5.3 两周工作安排

#### 第1周：质量瓶颈修复与演示链路

- 对所有深度大于等于1的候选链接执行相关性门槛，阻止相关度为0的导航、推荐和门户噪声占满队列。
- 将搜索预算与核心问题数量关联，并保留任务级硬上限，保证复杂专题仍有补充检索空间。
- 校准OCR环境，安装并验证中文高质量字库；纯照片无正文时应标记跳过，不生成无意义文本。
- 在支持Chromium sandbox的环境完成动态页面真实验证；宿主不支持sandbox时保持失败关闭。
- 在部署工作站完成Qwen3.6 27B双路基准，记录2路、256K和双路合计decode速度。
- 固定实验运行规范：`--max-turns 200`、搜索环境、模型版本、处理器版本和配置哈希必须写入manifest。
- 完成3个专题的人工基准准备，包括参考来源、关键事实和人工耗时记录表。

#### 第2周：真实运行、比较和演示

- 每个专题至少执行一次正式运行；失败任务修复后允许重跑一次，初次结果和重跑原因均须保留。
- 自动保存manifest、trace、run.log、状态快照、材料、报告、ANALYSIS和REPORT。
- 由业务人员盲审关键事实和引文，不向审阅者展示系统内部覆盖分数。
- 对同等难度任务记录人工流程和智能体辅助流程耗时，计算节省比例。
- 形成15分钟演示脚本：创建任务、观察采集、查看材料推荐、追溯引文、查看缺口、下载报告。

### 5.4 G1量化门禁

三个专题必须同时满足：

| 指标 | G1阈值 |
| --- | ---: |
| 成功形成正式报告的专题 | 3/3 |
| 正式任务使用本地Qwen3.6 27B且无云端回退 | 3/3 |
| 核心问题明确回答或明确披露缺口 | 100% |
| 随机抽查关键结论可定位到归档原文 | 100%，不少于20条 |
| 引文被人工判定为完整或基本支持事实 | 不低于90% |
| 伪造URL、伪造引文或不存在的来源 | 0条 |
| 已归档材料中人工判定相关的比例 | 不低于65% |
| 低相关导航/门户材料占比 | 不高于20% |
| 智能体辅助初稿耗时相对人工基准下降 | 不低于30% |
| P0/P1未关闭缺陷 | 0个 |

G1通过后，甲方获得的不是概念演示，而是3份真实报告、完整证据链和一份基于实际数据的效果对比表。

## 6. 第二阶段：一个月补齐一期全部功能

### 6.1 第3周：检索与采集质量

- 完成深层链接相关性门槛、单页出站链接上限和同任务URL硬去重。
- 将下载字节锁改为原子额度预留与结算，在不突破1 GiB总预算的前提下实现真实的4路跨域下载。
- 按核心问题数量分配搜索预算，并验证news搜索失败时general回退不额外消耗一次模型决策。
- 增加时效优先策略，使带时间范围的任务优先选择范围内来源，同时保留必要的历史背景。
- 完成重要单源数据的二次来源发现路径，并在无法交叉验证时明确标为来源转述。
- 减少相同参数的重复搜索、覆盖评估和报告生成调用。

### 6.2 第4周：动态网页与多媒体

- 完成JavaScript空壳识别、浏览器渲染、动态链接发现、原始HTML和渲染DOM双归档的联调。
- 验证浏览器逐导航robots检查、SSRF阻断、请求数、超时、下载字节和总任务预算。
- 完成PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、TXT、CSV的提取回归。
- 完成图片OCR质量分级：文字型图片提取、纯照片跳过、扫描PDF OCR和行号输出。

## 7. 第三阶段：一个月测试、完善和正式验收

### 7.1 10个真实专题样本集

最终验收在启动第7周前冻结10个专题：

| 类型 | 数量 | 最低材料要求 |
| --- | ---: | --- |

| 事件背景或冲突调查 | 1 | 至少存在一组相互矛盾或口径不同的材料 |
| 多媒体重点专题 | 1 | 同时包含图片和音频或视频材料 |

整个样本集还必须满足：至少3个专题包含JavaScript动态页面，至少5份PDF、3份Office、5张文字型图片、2段音频和2段视频；每个专题包含2—4个核心问题。

除真实专题外，另冻结一套不计入业务质量分数的专项夹具：20个静态HTML页面、20个支持范围内的动态页面；PDF、DOC、DOCX、XLS、XLSX、PPT、PPTX各5份；20张文字型图片和10张纯照片；10段清晰普通话音频和10段视频；不少于30个安全攻击用例和10个中断恢复用例。每类格式至少包含1个恰好达到上限的用例和1个超过上限的用例，用于验证边界计费、原件保留和证据禁用。专项夹具用于稳定复现格式、安全和恢复能力，真实专题用于评价业务效果，两类结果不得相互替代。

模型专项基准包含10轮双路同时请求，每路输入约8K且输出不少于1024 token；另对64K、128K和224K输入长度分别执行双路并行稳定性用例。吞吐以两路在共同解码时间窗内产生的总输出token数除以解码墙钟时间计算，不将prefill时间混入decode速度。

## 8. 量化验收指标

### 8.1 指标计算规则

所有比例保留一位小数。分母为0时该指标记为“不适用”，不得按100%计入总成绩。

| 指标 | 计算公式 | 样本与证据 |
| --- | --- | --- |
| 任务成功率 | 达到`done`且产出报告的任务数 ÷ 总任务数 | 10个冻结专题的task状态与output |
| 核心问题处理率 | 成功形成报告的任务中，已明确回答或明确披露缺口的问题数 ÷ 这些任务的核心问题总数 | 报告、coverage快照和人工评分 |
| 核心问题充分回答率 | 人工判定达到可用回答的问题数 ÷ 核心问题总数 | 双人独立评分，不一致时第三人裁决 |
| 引用可复核率 | 能定位到归档原文且文字一致的引文数 ÷ 抽查引文数 | 全部关键结论；其他随机抽查至总数不少于50条 |
| 引文支持率 | 人工判定完整或基本支持对应事实的引文数 ÷ 抽查引文数 | 与引用可复核率使用同一样本 |
| 交叉验证合规率 | 满足声明类型所需独立来源组的事实数 ÷ 需要交叉验证的事实数 | active facts、evidence和source_group |
| 有效材料率 | 人工判定与至少一个核心问题相关的材料数 ÷ 成功提取材料数 | 每专题全部成功提取材料 |
| 噪声材料率 | 导航、广告、无关推荐、空正文等材料数 ÷ 已归档材料数 | 材料人工标注表 |
| 多媒体提取成功率 | 生成可用正文且状态为complete的材料数 ÷ 支持且输入有效的材料数 | 冻结夹具和真实专题材料 |
| 格式边界判定准确率 | 在限材料正常处理且超限材料被准确阻断的用例数 ÷ 全部边界用例数 | 每格式上限值与超限值夹具 |
| 重复下载率 | 同任务中重复下载同一canonical URL的次数 ÷ 总下载次数 | crawl快照和访问日志 |
| HTTP有效并发数 | 受控慢响应站点测试中同时处于下载状态的请求峰值 | 四域名假站点和时序日志 |
| 双路合计decode速度 | 两路共同解码窗口内的总输出token数 ÷ 该窗口秒数 | 10轮双路基准，逐轮保留原始计数 |
| 双槽启用率 | 主Agent和辅助读任务同时就绪时两槽实际同时工作时长 ÷ 可并行时长 | 模型调度时序和请求ID |
| 主Agent槽位等待 | 主Agent请求入队到开始prefill的时间 | 全部真实专题的P50和P95 |
| 恢复成功率 | 恢复后从正确队列状态继续且产物完整的次数 ÷ 故障注入次数 | 每类中断至少2次，总计不少于10次 |
| 人工事实修改率 | 人工判定需实质修改的active事实数 ÷ active事实总数 | 修改前后对照；标点和排版不计 |
| 初稿提效比例 | 1－智能体辅助初稿人时 ÷ 纯人工初稿人时 | 至少3组同难度配对专题 |
| 材料筛选提效比例 | 1－智能体辅助筛选人时 ÷ 纯人工筛选人时 | 阅读日志与材料选择记录 |
| 业务时段可用率 | （约定业务时段分钟数－故障导致不可用分钟数）÷ 约定业务时段分钟数 | 第四阶段健康检查、每日测试任务与故障台账 |

## 9. 第四阶段：三个半月真实试运行

### 9.1 试运行范围

- 用户规模：1名固定业务用户，在一台本地工作站上使用；专业审阅人员只参与报告和引文复核，不计为并发用户。
- 任务规模：每月不少于10个真实任务，累计不少于35个。
- 运行方式：同时只有1个活跃调研任务，用户可提交后续任务并查看排队位置。
- 使用方式：标准任务优先使用定向抓取；明确需要附件目录或广覆盖时启用深度采集。
- 数据边界：只采集无需登录的公开信息；任务、材料和报告保存在甲方指定环境。
- 人工责任：所有对外发布、高风险判断和正式决策材料必须由业务人员复核。

### 9.2 月度运营节奏

每月执行一次固定复盘：

1. 汇总任务数、成功率、专题类型、耗时、模型请求与输出token、双路decode速度、槽位启用率、搜索次数、抓取数和下载字节。
2. 抽查不少于当月20%的任务，且至少3个；每个任务抽查关键结论和引用。
3. 统计失败原因、低星材料、人工修改、用户反馈和未关闭缺陷。
4. 对连续两个月出现的同类问题，必须形成根因修复，不再仅靠提示词或人工规避。
5. 发布月度运行报告和下一月改进清单。

### 9.3 G4最终复验阈值

试运行结束时同时满足：

- 累计真实任务不少于35个，任务成功率不低于90%。
- 最近连续两个月业务时段可用率不低于98%。
- 每月至少复跑1次双路基准，双路合计decode速度P50不低于45 token/s，试运行期间OOM和模型服务崩溃均为0。
- 抽查引用可复核率保持100%，引文支持率不低于95%。
- 人工事实修改率不高于10%，且无伪造来源或重大事实错误。
- 初稿提效比例不低于50%，材料筛选提效比例不低于40%。
- 固定业务用户至少对10个任务评分，5分制平均满意度不低于4.0，应评任务回收率不低于80%。
- P0/P1未关闭缺陷均为0；P2未关闭缺陷不超过5个。
- 完成备份恢复演练1次，恢复后的任务、材料、证据和报告完整率100%。

## 10. 验收组织与证据要求

### 10.1 甲方职责

- 提供10个冻结验收专题、核心问题、业务范围和必要的人工参考材料。
- 指定至少2名业务审阅人员和1名分歧裁决人员。
- 提供受控公网出口、部署资源、数据保留要求和安全限制。
- 记录纯人工基准耗时、智能体辅助耗时和实质修改内容。
- 对验收结果、遗留风险和试运行范围进行确认。

### 10.2 乙方职责

- 提供安装包、依赖清单、配置样例、部署说明、操作手册和故障排查手册。
- 固定验收版本、Git提交、模型与搜索配置、依赖版本和配置哈希。
- 完整保存每次验收运行的trace、manifest、日志、状态快照、材料和输出报告。
- 提供指标计算表、缺陷台账、修复证据和复测结果。
- 保证验收过程不通过修改题目、删除失败样本或人工补写来源提高结果。

### 10.3 每个专题的验收证据包

每个专题至少包含：

- 任务输入、核心问题和范围冻结记录。
- `manifest.json`、`trace.jsonl`和`run.log`。
- 任务、覆盖、事实、证据、冲突、材料和采集队列状态快照。
- 原始材料、提取正文、渲染DOM和SHA-256记录。
- 正式调研报告、材料摘要、阅读推荐和来源目录。
- 自动分析结果、人工评分表、修改记录和缺陷关联编号。

缺少原始运行轨迹或人工评分依据的指标不得计入通过结果。

### 10.4 正式验收流程

1. 冻结验收版本、环境、配置和10个专题。
2. 执行环境前置检查，确认搜索、Tesseract、FFmpeg、faster-whisper、LibreOffice、Playwright和Chromium状态。
3. 依次执行10个专题，保留所有首次运行结果。
4. 自动生成分析数据，业务人员独立盲审。
5. 汇总指标并登记缺陷，关闭P0/P1。
6. 只复跑受缺陷影响的专题和专项用例，保留前后对比。
7. 甲乙双方确认G3结果，进入试运行。
8. 试运行结束后依据G4指标形成最终验收结论。

### 11.2 实施纪律

- 每项行为变化先增加失败测试，再做最小实现和回归验证。
- 每次实验只验证1—2个核心假设，主题和评分口径保持不变。
- 所有提交遵循小范围Conventional Commit，不混入运行数据、API密钥和无关文件。
- 每个阶段结束运行Ruff、Pyright、全部pytest、Python构建，以及Bun测试、类型检查和生产构建。
- 外部程序在自动化测试中使用mock；验收环境另执行真实处理器和真实Chromium测试。
- 新增逻辑至少有一项能在回归时失败的自动检查；安全边界必须覆盖允许和拒绝两类用例。

## 12. 风险与处置

| 风险 | 预警信号 | 处置方式 |
| --- | --- | --- |
| 外部搜索或网站不稳定 | 连续搜索为空、429/5xx增加 | 启用同预算降级、记录外部故障、保留有缺口报告 |
| 垃圾链接再次换形态 | 有效材料率下降、rel=0材料增加 | 追溯入队来源，修复统一相关性门槛并复跑固定专题 |
| 模型重复调用 | 请求量接近200、相同工具连续调用 | 使用状态门控和幂等键阻断无进展调用 |
| 双路长上下文导致资源耗尽 | 显存超过95%、decode低于40 token/s或出现OOM | 保持64K/128K常规预算和224K硬上限，不增加第三槽位，重媒体与Qwen不抢占加速器 |
| 多媒体环境不完整 | `/api/system`显示处理器不可用 | 验收前停止执行，补齐依赖后重新做环境检查 |
| 浏览器宿主不支持sandbox | Chromium启动失败 | 更换支持用户命名空间或SUID sandbox的隔离宿主，不允许关闭sandbox验收 |
| 人工评分不一致 | 两名审阅者差异超过10个百分点 | 由第三人裁决并记录评分规则修订 |
| 真实专题难度差异大 | 耗时和覆盖出现极端值 | 同时报告中位数、P90和逐题结果，不用平均值掩盖异常 |
| 进度压力挤占测试 | P0/P1未关闭仍计划进入下一阶段 | 阶段门禁不放行，调整范围但不降低安全和证据标准 |

## 13. 项目完成定义

本期项目只有在以下条件全部满足后才视为完成：

1. G1、G2、G3和G4均有书面记录并通过。
2. 10个冻结专题和不少于35个试运行任务的数据完整可查。
3. 一票否决项全部通过，P0/P1未关闭缺陷为0。
4. 甲方能够在本地环境独立创建任务、查看进度、核查引文、下载材料和报告、执行取消及恢复。
5. 安装、配置、运行、备份、恢复、故障处理和验收文档齐全。
6. 所有验收指标均能从系统状态、运行轨迹、归档材料或人工评分表复算。

满足上述条件后，系统可作为单部门公开信息调研辅助工具进入常态使用；多部门协作、内部知识接入和平台化扩展另行立项。
