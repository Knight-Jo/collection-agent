## 1. 文档目的

本文综合以下内容，形成后续项目开发的统一方向：

- [情报搜集智能体设计思路与关键能力总结报告](./search_policy.md)；
- 当前 `src/intel_agent/` 实现；
- [实验路线与历次真实运行结论](../experiments/ROADMAP.md)；
- 本地和远程 Qwen 模型在受限上下文、低吞吐场景中的运行结果。

本文不是新的产品宣传材料，也不是逐文件编码计划。它用于回答：

1. 当前系统已经具备什么能力；
2. 当前瓶颈在哪里；
3. 后续开发应按什么顺序推进；
4. 每项工作应落到哪些模块；
5. 如何用可量化指标验收，而不是以“任务完成”或“抓取数量”代替质量判断。

## 2. 总体结论

项目已经具备一条可靠的证据治理主链：

```text
Task
  → Research Question
  → Search / Crawl / Document
  → Fact / Evidence
  → Semantic Review
  → Coverage / Conflict
  → Material Digest
  → Research Report
```

当前最成熟的能力不是搜索引擎数量，也不是大模型生成能力，而是：

- 任务、问题、事实、证据和文档之间具有稳定 ID 关联；
- 原始材料和抽取文本具有哈希与完整性校验；
- 只有语义审核为 `full` 的证据才能进入覆盖和正式报告；
- 独立来源、时效范围、冲突和反证进入确定性覆盖判断；
- 报告和完成摘要以持久化证据为权威，不接受模型自由文本夸大；
- 深度抓取支持恢复、robots、限速、SSRF 防护和多媒体抽取。

真实实验同时证明，下一阶段的主要矛盾已经从“能不能抓取和生成报告”转为：

> 如何在有限搜索、时间、Token 和本地推理吞吐预算下，把候选资源稳定转化为覆盖关键问题的独立有效证据。

因此，后续不应优先继续提高 `max_urls`、`max_depth`、搜索次数或模型上下文，而应优先建设：

1. 问题与来源维度的证据覆盖矩阵；
2. 覆盖缺口驱动的确定性动作选择；
3. 查询、候选、文档、证据之间的完整追踪；
4. 站点级资源发现与问题感知的抓取调度；
5. Evidence Gain 驱动的停止判断和量化评测。

## 3. 当前能力基线

### 3.1 已经具备的核心能力

| 领域 | 当前实现 | 主要模块 |
|---|---|---|
| 任务规划 | 主题、目标、2–6 个关键问题、时间/地域/语言范围、充分性标准 | `models.py`、`task.py`、`runner.py` |
| 查询生成 | 发现、一手来源、验证、结构化数据、附件、反证六槽查询矩阵 | `search_queries.py` |
| 多引擎搜索 | SearXNG、Bing、百度、百度新闻并行召回 | `search.py` |
| Search/Fetch 分离 | 搜索结果只作为候选，正式证据必须先归档 | `agent.py`、`fetch.py` |
| 深度采集 | 持久 frontier、URL 去重、域名配额、来源轮转、断点恢复 | `crawl.py`、`storage.py` |
| 动态页面 | 静态正文不足时可选 Playwright 渲染 | `browser.py`、`crawl.py` |
| 多媒体提取 | PDF、Office、图片 OCR、音视频转写、纯文本 | `extract.py` |
| 证据治理 | 精确引文、语义审核、冲突、来源组、哈希校验 | `evidence.py`、`audit.py`、`conflicts.py` |
| 覆盖评估 | 问题覆盖、独立来源、高质量来源、时效和无进展停止 | `coverage.py` |
| 阅读辅助 | 1–5 星阅读推荐、材料摘要、阅读顺序 | `materials.py`、`report.py` |
| 上下文管理 | 16K–256K 可配窗口、工具结果压缩、阶段恢复和确定性续跑 | `context.py`、`runner.py` |
| 实验评测 | manifest、trace、状态快照、报告和转化漏斗 | `scripts/run_experiment.py`、`scripts/analyze_run.py` |

### 3.2 已被实验验证的关键结论

1. 单纯扩大搜索和抓取规模不能保证研究质量。011 实验归档 143 篇文档，但只有 8 篇进入证据链，文档证据利用率为 5.6%。
2. 域名配额和来源轮转能抑制论坛洪泛，但不能凭空创造高质量种子；搜索输入质量与抓取调度必须共同改进。
3. 确定性查询矩阵提高了查询广度，但如果模型不执行补证闭环，仍然无法形成双源事实。
4. 判定层门控比提示词更可靠。单源 backlog 门控曾将双源率从 0% 提高到 86.7%。
5. 过强门控必须同时具备预算耗尽和无进展出口，允许任务诚实地以 `with_gaps` 完成。
6. 本地小模型更需要明确的持久状态和唯一下一动作，而不是更长的提示词。
7. 033 实验已经能够安全完成报告，但只有 1 条 `full` 事实，说明报告安全性已基本解决，搜索和证据供给成为主要瓶颈。

## 4. 当前主要问题

### 4.1 查询矩阵不等于证据覆盖矩阵

当前 `search_matrix.json` 记录了问题、查询槽位、阶段、搜索结果和新域，但不能直接回答：

- 某个问题缺少哪类来源；
- 某类来源产生了多少有效文档；
- 哪些文档形成了 `full` 证据；
- 哪些来源属于同一独立来源组；
- 哪个搜索动作真正降低了覆盖缺口；
- 哪个矩阵格子已经充分、无结果或存在冲突。

因此当前系统仍容易“按计划执行查询”，而不是“根据覆盖缺口选择下一步最有价值的动作”。

### 4.2 查询调度缺少问题公平性

查询阶段预算目前由整个任务共享，并按问题顺序执行。前面的关键问题可能先消耗发现或验证预算，使后续问题、附件查询或反证查询得不到执行机会。

矩阵查询还固定使用 `general`、`zh-CN`，并将 `time_range` 记录为 `None`。问题中的语言和时间约束没有完整传递到实际搜索调用。

### 4.3 搜索结果治理仍然偏弱

搜索层存在以下不足：

- URL 去重规则弱于抓取层 canonicalization；
- 跨查询、跨搜索引擎的同一候选没有统一台账；
- 搜索结果按来源类型优先，再按关键词命中排序，不是问题意图感知的综合排序；
- 没有完整记录候选为何被抓取、忽略、去重或拒绝；
- `new_domain` 主要按 hostname 判断，可能把同一注册域的不同子域误当成新来源；
- 缺少搜索引擎级成功率、延迟、结果数和降级原因。

### 4.4 信息空间探索不足

当前已经能沿正文链接递归抓取资源，但尚未系统覆盖：

- `robots.txt` 声明的 Sitemap；
- Sitemap 索引和站点地图；
- RSS/Atom；
- 下载中心、公告中心和文档中心入口；
- 页面声明的 alternate feed；
- 站点公开子域和公开数据目录；
- 从材料中发现的客户、供应商、投资机构、监管机构等实体入口。

系统已经具备资源解析能力，但资源发现供给仍不足，因此多媒体查询存在“支持格式很多、真实命中很少”的情况。

### 4.5 本地材料检索不够稳健

当前 `document_search` 要求查询词全部出现在正文中，并主要按词频、来源类型和新来源组排序。这会漏掉：

- 同义表达；
- 中英文实体别名；
- 标题相关但正文用词不同的文档；
- 只命中部分高价值关键词的文档；
- 能够补充第二来源但词频较低的材料。

### 4.6 停止条件缺少直接的证据增益

当前通过 `gap_score` 和连续两轮无下降实现 `no_progress`，方向正确，但它仍然是覆盖快照级判断。系统尚未直接记录每次搜索、抓取和阅读带来的：

- 新增 `full` 证据；
- 新增独立来源组；
- 新覆盖的问题/来源格子；
- 新发现的冲突或反证；
- 对报告核心结论的实际贡献。

### 4.7 Trace 尚未成为统一底层数据

当前状态分散在任务、查询矩阵、crawl、document、fact、evidence、coverage 和实验 trace 中。CLI trace 主要在任务结束后一次性写入，异常退出可能丢失模型请求、工具调用和最后错误。

目前尚不能稳定重建：

```text
Goal → Question → Gap → Decision → Action
→ Observation → Evidence → State Update
```

## 5. 目标架构

### 5.1 目标主链

```text
用户目标与约束
       │
       ▼
关键问题与最低证据要求
       │
       ▼
覆盖矩阵派生视图 ◄──────────────┐
       │                         │
       ▼                         │
覆盖缺口与下一动作               │
       │                         │
       ▼                         │
Search Decision                 │
       │                         │
       ├── 搜索引擎发现          │
       ├── 已知权威源直取        │
       ├── 站点结构发现          │
       ├── 本地文档补证          │
       └── 受控实体扩展          │
       │                         │
       ▼                         │
Candidate Ledger                │
       │                         │
       ▼                         │
Fetch / Crawl / Browser         │
       │                         │
       ▼                         │
Parser / OCR / ASR              │
       │                         │
       ▼                         │
Document → Fact → Evidence      │
       │                         │
       ▼                         │
Audit / Conflict / Coverage ────┘
       │
       ▼
Evidence Gain / Stop Decision
       │
       ▼
Material Digest / Report
```

### 5.2 权威数据边界

后续开发必须坚持单一事实源原则：

| 数据 | 权威来源 |
|---|---|
| 任务与问题 | `IntelTask` |
| 原始材料与抽取状态 | `IntelDocument`、`CrawlSnapshot` |
| 原子事实 | `Fact` |
| 精确引文关系 | `EvidenceSupport` |
| 证据语义判定 | `SupportReview` |
| 冲突 | `EvidenceConflict` |
| 当前充分性 | `CoverageSnapshot` 及其 fingerprint |
| 正式交付物 | 与 coverage fingerprint 绑定的 output |

以下内容只能作为派生视图或观察数据，不得成为第二份权威状态：

- 搜索覆盖矩阵；
- Candidate Ledger；
- Evidence Gain；
- 搜索漏斗；
- Web 仪表盘统计；
- 实验评测指标。

派生数据必须能够由任务、搜索轨迹、文档、证据和覆盖状态重新计算。缓存可以存在，但删除缓存后必须可重建。

## 6. 核心开发方向

### 6.1 P0：问题 × 来源证据覆盖矩阵

#### 目标

把“搜得充分”变成可计算、可解释、可指导下一动作的状态。

#### 建议结构

矩阵行是关键问题，列是适用于该问题的来源角色：

- `official`：企业、机构、项目方原始材料；
- `government`：政府、监管、司法和公共机构；
- `news`：具有独立采编能力的媒体；
- `academic`：论文、研究机构和高校；
- `industry`：行业协会、咨询报告和专业资料；
- `structured`：数据库、交易所数据、统计表和公开数据集；
- `social`：社区、社交媒体、用户反馈和反证线索。

每个格子至少计算：

```text
question_id
source_role
applicability
search_count
candidate_count
archived_document_count
read_document_count
full_evidence_count
independent_source_groups
conflict_count
last_searched_at
evidence_gain
status
```

状态建议限定为：

```text
not_applicable
planned
searched
candidate_found
acquired
evidenced
covered
conflicted
```

#### 实现原则

1. 第一版只做派生计算，不新增持久化权威模型。
2. 不要求每个问题覆盖所有来源类型。
3. `other` 可以统计，但不作为计划中的来源角色。
4. `covered` 必须来自现有 `full` evidence 和 coverage 规则，不得由搜索数量推断。
5. 一个 URL、一个域名或多篇转载都不等于多个独立来源组。

#### 推荐落点

- 首选在 `coverage.py` 中增加派生函数；只有文件职责明显过大时再拆出 `coverage_matrix.py`。
- 在 `web/views.py` 中投影给任务详情页。
- 在 `scripts/analyze_run.py` 中输出矩阵摘要和跨实验对比。

### 6.2 P0：覆盖缺口驱动的下一动作

#### 目标

让系统从“按固定顺序执行 Query”升级为“根据当前缺口选择最有价值的动作”。

#### 动作优先级

```text
1. 未回答的核心问题
2. 已有事实但没有 full evidence
3. 单源事实缺少第二独立来源
4. 缺少一手/高质量来源
5. 缺少指定时间范围内材料
6. 存在未处理冲突或反证
7. 适用的结构化数据或附件尚未搜索
8. 一般性背景扩展
```

动作输出至少包含：

```text
question_id
gap_type
action_type
target_source_roles
query_slot
query
language
time_range
reason
```

#### 实现原则

- 由确定性代码根据 coverage 和已有轨迹选择缺口；模型负责生成或调整具体 Query。
- Query 必须通过 Pydantic 边界校验。
- 同一问题的最低来源槽位满足前，不得让另一个问题持续独占全部预算。
- 附件和多媒体查询按问题适用性启用，不应所有任务强制执行全格式搜索。
- 搜索预算耗尽或连续无收益时必须允许 `with_gaps` 结束。

#### 推荐落点

- `search_queries.py`：生成带元数据的查询意图。
- `agent.py`：替换当前按固定问题顺序推进矩阵的调度方式。
- `models.py`：如需要持久化计划元数据，只增加最小、向后兼容的模型字段。

### 6.3 P0：统一候选台账与排序

#### 目标

让跨查询、跨引擎发现的同一资源只有一个候选身份，同时保留全部发现来源和排名信号。

#### 候选最小字段

```text
canonical_url
question_ids
discovery_queries
query_slots
engines_and_ranks
source_group
source_type
first_seen_at
last_seen_at
fetchable
archived_document_id
decision
decision_reason
```

#### 必须完成

1. 搜索层复用抓取层完整 URL canonicalization。
2. 跨查询按 canonical URL 去重，不丢失多个查询和引擎的观测。
3. `new_domain` 使用注册域或 `source_group`，不是裸 hostname。
4. 每个候选必须有最终处置：抓取、已归档、重复、低相关、配额限制、不安全或失败。
5. 排序先执行主题实体最低相关性门槛，再综合：
   - 查询意图匹配；
   - 来源角色；
   - 时间范围；
   - 新来源组；
   - 多引擎共同命中；
   - 搜索排名；
   - 可抓取性。
6. 来源权威性是加分项，不能让不相关的政府页面无条件排在高度相关材料之前。

第一版可采用确定性加权分数或 Reciprocal Rank Fusion，不需要训练独立排序模型。

### 6.4 P0：统一增量 Trace

#### 目标

使正常完成、超时、取消、模型错误和进程异常都能保留可分析轨迹。

#### 事件结构

```text
event_id
task_id
timestamp
event_type
question_id
gap_type
parent_event_id
action
observation
state_before_fingerprint
state_after_fingerprint
usage
latency_ms
error
```

建议事件类型：

```text
task.planned
gap.detected
search.decided
search.completed
candidate.decided
fetch.completed
extract.completed
document.read
fact.saved
evidence.saved
evidence.reviewed
coverage.updated
research.stopped
report.generated
```

#### 实现原则

- Trace 是观察日志，不参与事实和覆盖判定。
- 每个事件完成后立即追加，不能等整个 Agent 结束后一次性写入。
- JSONL 最后一行损坏时允许跳过，不影响之前事件读取。
- 事件只保存必要内容；大正文引用 document ID 和行号，不复制全文。
- Web SSE、CLI trace 和实验分析应投影同一事件，不分别定义三套语义。

#### 推荐落点

- `storage.py`：提供任务级安全追加和容错读取。
- `runner.py`、`agent.py`：记录模型和研究动作。
- `crawl.py`：将现有 crawl 事件投影到统一事件结构。
- `main.py`：不再只在运行结束后保存完整轨迹。
- `web/runs.py`：从统一事件流生成 SSE。

### 6.5 P1：站点级资源发现

#### 目标

在找到高价值网站后，系统能够主动发现站点内的公开信息空间，而不是只遍历单个页面的正文链接。

#### 第一阶段支持

- `robots.txt` 中声明的 Sitemap；
- Sitemap 和 Sitemap Index；
- RSS/Atom；
- 页面中的 `<link rel="alternate">`；
- 页面可见的公告、下载、新闻和文档中心链接；
- 页面附件链接及 `Content-Disposition` 文件名；
- 同源、公开、经过安全校验的资源链接。

#### 暂缓支持

- 自动登录；
- 绕过验证码；
- 猜测私有 API；
- 批量扫描子域；
- 绕过 robots 或访问控制；
- 无限制保存浏览器网络请求；
- iframe、弹窗或跨域脚本中未验证的资源自动执行。

所有新入口必须复用现有 URL 安全校验、DNS/重定向检查、robots、域名并发、延迟、总字节和单文件大小限制。

### 6.6 P1：问题感知的抓取调度

#### 目标

将当前“来源类型 → 注册域”的公平轮转扩展为：

```text
关键问题 → 缺口/来源角色 → 注册域 → URL 优先级
```

#### CrawlEntry 建议增加的兼容字段

```text
question_ids: []
discovery_method: search | direct_source | sitemap | rss | page_link | entity
query_slots: []
target_source_roles: []
```

旧任务缺少这些字段时使用空列表和 `page_link`/`search` 兼容推断，不要求数据迁移。

调度必须继续遵守：

- 同任务 canonical URL 硬去重；
- 非一手域配额；
- 社交/论坛总量限制；
- 来源类型和注册域轮转；
- depth、相关性、附件价值和安全限制；
- 取消后恢复 queued 状态。

### 6.7 P1：本地材料补证与 Evidence Yield

#### 目标

优先消费已经付出抓取和提取成本的本地材料，再进行新的互联网搜索。

#### 实施顺序

1. 改善现有词法检索，允许部分高价值关键词命中并增加标题权重。
2. 为问题时间范围、来源角色和新来源组增加过滤/加权。
3. 对单源事实直接检索其声明中的主体、动作、数字和时间。
4. 对冲突分别检索双方口径。
5. 当词法检索在固定基准上仍明显漏召回时，再引入 SQLite FTS5/BM25。
6. 向量检索只作为可重建的候选重排层；没有测量到词法召回缺口前不引入 embedding 服务。

SQLite 索引或向量索引不得成为文档正文的权威存储，必须能够由 `IntelDocument.text_path` 重建。

### 6.8 P1：来源独立性与传播关系

#### 目标

在当前注册域分组和完全相同正文哈希去重基础上，识别轻度改写、节选和转载关系。

#### 最小实现

综合使用：

- 规范化正文哈希；
- 标题相似度；
- 正文分片相似度；
- 页面中的“来源/转载自”字段；
- canonical、原文和引用链接；
- 发布时间先后关系。

输出关系限定为：

```text
original
repost
quoted
near_duplicate
unknown
```

只有能够确认独立生产信息的来源组才计入多源验证。无法判断时保持 `unknown`，不得自动认定独立或转载。

### 6.9 P2：受控实体扩展

#### 目标

从材料中发现新的检索入口，例如子公司、产品、客户、供应商、投资机构、合作伙伴、竞争对手和监管机构。

#### 约束

- 新实体必须来自已归档文档，并保存证据行号；
- 必须关联原关键问题和扩展原因；
- 第一版只生成待执行建议，不自动无限扩展；
- 每个问题设置实体建议和扩展搜索上限；
- 连续扩展没有产生新证据时停止；
- 不引入图数据库，先使用任务级 JSON 和派生关系视图。

### 6.10 P2：受控动态问题树

#### 目标

允许研究过程中提出新增、拆分、合并或降级问题的建议，同时保持任务可复现、可评测和可停止。

#### 第一版只实现 Question Proposal

```text
proposal_id
task_id
action
target_question_ids
proposed_text
reason
evidence_ids
expected_coverage_value
status: suggested | accepted | rejected
created_at
```

初始问题不直接修改。只有用户确认，或符合严格自动接受规则且不超过问题数量上限时，才生成新的稳定 question ID。

## 7. Evidence Gain 与停止策略

### 7.1 Evidence Gain 定义

每个研究动作完成后计算增量：

```text
Evidence Gain =
  新增 full evidence
  + 新增独立来源组
  + 新覆盖矩阵格子
  + 新发现的重要冲突/反证
```

具体实现可以保存分项计数，不必过早合成一个带主观权重的总分。

### 7.2 停止条件

满足以下任一条件可以停止：

1. 所有核心问题达到充分性要求；
2. 连续两轮定向动作没有新增 full evidence、独立来源组或覆盖格子；
3. 每个剩余缺口都执行过对应来源和时间范围的定向搜索，仍无候选；
4. 搜索或抓取预算耗尽；
5. 外部处理器、网络或公开数据条件导致剩余缺口不可完成。

停止后必须记录：

- 停止原因；
- 未覆盖的问题和矩阵格子；
- 已尝试的查询和来源；
- 不可获取或无法验证的原因；
- `sufficient` 或 `with_gaps`。

发现新冲突虽然可能使 `gap_score` 上升，但属于有价值的信息增益，不能被视为无进展。

## 8. 模型与确定性代码的职责边界

### 8.1 模型适合负责

- 理解调研目标；
- 初始关键问题建议；
- 根据确定性缺口生成专业 Query；
- 从材料中提出原子事实候选；
- 证据语义蕴含审核；
- 受控实体或问题扩展建议；
- 在系统限定的事实和证据内组织报告表述。

### 8.2 确定性代码必须负责

- ID、状态和预算；
- URL canonicalization、去重和安全校验；
- 查询调度公平性；
- 候选处置状态；
- 文档哈希和完整性；
- 独立来源组计数；
- 时效和时间范围判定；
- Evidence Gain 统计；
- 覆盖与停止条件；
- 报告证据门控；
- Trace 持久化；
- 最终完成状态和摘要。

在 16K–256K 上下文和低吞吐本地模型环境下，应优先把可确定计算从提示词移到代码。扩大上下文或提高输出 Token 不能替代状态机、调度和证据约束。

## 9. 模块与文件级开发落点

| 文件/模块 | 建议职责变化 |
|---|---|
| `models.py` | 仅增加必要且向后兼容的查询意图、事件或提案字段 |
| `task.py` | 维护任务预算、阶段和停止原因，不承载搜索排序 |
| `search_queries.py` | 生成带 question/gap/source/language/time 元数据的查询意图 |
| `search.py` | 多引擎观测、统一 canonical URL、候选融合与引擎健康统计 |
| `agent.py` | 根据确定性下一动作调工具，逐步缩小当前过多的搜索编排职责 |
| `crawl.py` | 问题感知调度、站点发现入口、现有安全和预算约束 |
| `extract.py` | 保持资源类型分派和处理器质量门控，不承担搜索策略 |
| `document_search` | 从严格全词匹配演进为问题/缺口感知的本地补证检索 |
| `coverage.py` | 覆盖矩阵派生、Evidence Gain 和下一缺口输入 |
| `storage.py` | 统一事件增量追加、容错读取和派生索引重建支持 |
| `materials.py` | 使用覆盖贡献和阅读价值生成推荐，不参与证据判定 |
| `report.py` | 继续只接受已审核且处于当前 coverage fingerprint 的事实 |
| `runner.py` | 阶段恢复、唯一下一动作和任务级累计模型预算 |
| `main.py` | 增量 trace 接入，不再依赖结束后一次性保存 |
| `web/views.py` | 输出覆盖矩阵、候选漏斗、停止原因和来源链派生视图 |
| `web/runs.py` | 将统一事件投影为 SSE |
| `scripts/analyze_run.py` | 统一计算质量、覆盖、收益和效率指标 |

不建议在首轮同时大规模拆分 `agent.py`。应先把确定性计算移到已经存在的 `coverage.py`、`search_queries.py` 和 `crawl.py`；只有职责边界稳定后再做机械拆分。

## 10. 分阶段实施顺序

### 阶段 A：证据覆盖控制面（P0）

按以下顺序实施：

1. 覆盖矩阵派生视图；
2. 缺口到下一动作的确定性映射；
3. 问题公平的查询调度和时间/语言透传；
4. 跨查询 Candidate Ledger 与统一 URL 去重；
5. 增量统一 Trace；
6. Evidence Gain 和停止原因。

完成阶段 A 后，系统应能解释：

> 当前缺什么、为什么执行这个动作、动作产生了什么、状态如何变化、为什么继续或停止。

### 阶段 B：信息空间发现与转化效率（P1）

1. Sitemap/RSS/下载中心发现；
2. 问题感知抓取调度；
3. 本地材料补证排序；
4. 近重复和来源传播关系；
5. 多媒体专项数据集复测；
6. Web 覆盖矩阵和漏斗视图。

完成阶段 B 后，应在不扩大总预算的前提下提高：

- 有效来源数量；
- 文档证据利用率；
- 双源事实比例；
- 多媒体目标资源命中；
- 单位搜索和单位 Token 的 full evidence 产出。

### 阶段 C：受控自适应与数据闭环（P2）

1. 实体扩展建议；
2. Question Proposal；
3. 教师模型与本地模型轨迹对比；
4. 策略错误归因；
5. 可用于蒸馏和 benchmark 的标准轨迹数据集。

只有阶段 A、B 的状态和指标可靠后，才进入阶段 C。否则动态实体和问题树只会放大目标漂移和成本失控。

## 11. 量化验收标准

### 11.1 状态和可追溯性

| 指标 | 验收目标 |
|---|---:|
| Search Query 绑定 question_id | 100% |
| Search Query 绑定 gap_type/decision reason | 100% |
| 候选 URL 有最终处置原因 | 100% |
| 文档可追溯到发现动作 | 100% |
| Evidence 可追溯到文档和行号/时间戳 | 100% |
| Coverage 可追溯到 full review | 100% |
| 异常退出后已完成事件保留率 | 100% |
| 派生矩阵与权威 evidence/coverage 一致 | 100% |

### 11.2 搜索质量

| 指标 | 验收目标 |
|---|---:|
| Precision@10 | ≥70% |
| 必找来源 Recall@50 | ≥80% |
| 适用任务 Authoritative@10 | ≥40% |
| 时间约束任务 InScope@10 | ≥70% |
| 跨查询 canonical URL 重复率 | ≤5% |
| 无关日历/节假日等主题污染回归 | 0 条进入抓取队列 |

### 11.3 来源与覆盖

| 指标 | 验收目标 |
|---|---:|
| 每个核心问题一手候选 | ≥1 个 |
| 每个核心问题独立验证候选 | ≥2 个来源组 |
| 最大非一手域占比 | ≤15% |
| 前两域占比 | ≤35% |
| 有效域数量 | ≥6 |
| 社交/论坛占比 | ≤10% |
| 近重复材料占比 | ≤10% |
| 关键数字双源验证率 | 100% |
| 报告无证据事实 | 0 |

### 11.4 转化与效率

| 指标 | 验收目标 |
|---|---:|
| 文档证据利用率 | ≥20% |
| 已读文档形成 evidence 的比例 | 持续记录并相对基线提高 ≥30% |
| full evidence / Search Query | 相同基准任务较当前基线提高 ≥30% |
| full evidence / Fetch | 相同基准任务较当前基线提高 ≥30% |
| Token / full evidence | 相同模型和任务下较基线下降 ≥20% |
| 连续两轮零 Evidence Gain 后继续泛搜 | 0 次 |

阈值不能通过减少问题、降低来源标准、关闭时效要求或删除失败样本达成。无法计算的指标必须报告“不可计算”并说明缺少的观测数据。

## 12. 评测数据集设计

自动化测试和真实联网实验必须分层：

### 12.1 确定性夹具

用于验证：

- 覆盖矩阵计算；
- 问题和来源调度公平性；
- URL canonicalization；
- 搜索结果融合；
- Sitemap/RSS/附件发现；
- 来源传播关系；
- Evidence Gain；
- Trace 异常恢复；
- 停止条件和 `with_gaps` 出口。

### 12.2 冻结公开语料

保存许可允许的公开页面快照或最小夹具，用于稳定测量：

- Precision@10；
- 必找来源召回；
- 文档检索召回；
- 独立来源识别；
- 关键事实双源率；
- 报告证据一致性。

### 12.3 真实联网任务

至少覆盖：

1. 企业发展与商业化；
2. 政策与监管；
3. 投融资与财务数据；
4. 技术路线与学术研究；
5. 重大事件与争议；
6. 动态网页和多媒体专项。

每个任务提前定义必找来源、必须回答维度、已知冲突和适用资源格式。普通研究质量实验与多媒体专项实验不得继续共用一个无法命中目标格式的主题。

## 13. 安全与合规边界

后续扩展不得削弱现有安全约束：

- 只采集无需登录的公开 HTTP/HTTPS 内容；
- 遵守 robots.txt；
- 保持 DNS pinning、逐跳重定向验证和 SSRF 防护；
- 浏览器只在静态抓取不足时启用；
- 浏览器请求继续受域名、并发、数量和字节预算约束；
- 不自动绕过验证码、登录、付费墙或访问控制；
- 不执行网页中的命令、脚本指令或提示注入内容；
- 脚本、可执行文件、压缩包和不支持类型继续拒绝；
- 处理器缺失时保留原件、标记 unavailable，不进入证据；
- 对外下载继续执行哈希校验、attachment 和 `nosniff`；
- 新增站点发现和公开接口发现必须走与普通 URL 相同的安全检查。

## 14. 明确不做事项

在现阶段不应优先建设：

- Celery、Redis、Scrapy 等分布式调度系统；
- 独立图数据库；
- 只有一个实现的 Fetcher/Parser 插件框架；
- 为排序单独训练模型；
- 未经评测证明必要的向量数据库；
- 自动无限扩展实体和问题；
- 提高抓取深度和数量来掩盖搜索质量问题；
- 用更长提示词代替确定性状态和门控；
- 用搜索结果数、归档文档数、`stage=done` 或 `gap_score=0` 单独证明成功。

当前 `extract_resource` 的资源类型分派已经能够满足扩展需要。只有当新增处理器开始频繁修改同一分派逻辑、需要第三方独立发布或运行时装载时，才考虑正式插件接口。

## 15. 开发执行规则

1. 每个实验只验证一个主要假设，不同时改搜索、抓取、覆盖和模型参数。
2. 先写确定性失败测试，再修改实现。
3. 新状态字段必须提供旧任务默认值，不要求批量迁移历史 JSON。
4. 新指标必须明确分子、分母和不可计算条件。
5. 计划指标和真实运行结果必须分开记录。
6. 不得通过提示词替代可由代码确定的预算、调度、校验和停止规则。
7. 任何硬门控必须设计诚实出口和错误信息。
8. 任何缓存和索引必须可由权威状态重建。
9. 任何排序调整必须在固定基准上同时报告质量和成本变化。
10. 每项开发完成后运行 Ruff、Pyright、pytest；涉及 Web 时增加 Bun 测试、类型检查和构建。

## 16. 阶段完成定义

### 阶段 A 完成

- 覆盖矩阵可由现有状态重建；
- 每个查询可追溯到问题、缺口和决策原因；
- 每个候选有完整处置状态；
- Trace 在异常退出后仍保留已完成事件；
- 系统能给出唯一、可执行的下一动作；
- 停止原因包含 Evidence Gain 和剩余缺口。

### 阶段 B 完成

- Sitemap/RSS/下载中心产生非零有效资源样本；
- 抓取队列实现问题、来源角色和域名三层公平性；
- 文档证据利用率达到 20%；
- 关键数字双源验证率达到 100%；
- 多媒体专项中的目标格式均至少成功归档和提取 1 份；
- 搜索和证据效率指标相对固定基线改善。

### 阶段 C 完成

- 实体和问题扩展均有证据、原因、预算和审计记录；
- 动态扩展不会破坏停止条件和任务复现；
- 教师模型与本地模型使用同一 Trace 和指标比较；
- 轨迹能够直接用于策略分析、错误归因和蒸馏数据构建。

## 17. 最终开发方向

本项目后续需要优化的不是“让 Agent 搜索更多”，而是：

> 在单机、本地模型和有限公网条件下，用确定性控制面管理搜索空间，使每一次查询、抓取、阅读和审核都面向明确的关键问题与覆盖缺口，并最大化单位资源预算产生的独立有效证据。

开发优先级必须保持：

```text
权威证据状态
  > 覆盖矩阵与缺口
  > 搜索决策和候选治理
  > 站点与资源发现
  > 受控自适应
  > 更大预算和更复杂基础设施
```

这条路线既保留了现有实现最有价值的证据安全能力，也能逐步补齐搜索质量、覆盖广度、研究深度和运行可解释性，最终形成区别于一般云端 Research Agent 的本地专用情报调研系统。
