# Qwen3.8-27B 与 DeepSeek-V4-Flash 情报调研智能体运行对比分析

> 分析日期：2026-08-24  
> 实验主题：量子计算产业发展情况/状况  
> 分析对象：两次真实联网任务的结构化轨迹、任务状态、覆盖快照、材料清单和最终报告

## 一、执行摘要与选模结论

本次分析对比了本地 Qwen3.8-27B-AWQ-4bit 与云端
DeepSeek-V4-Flash 驱动情报调研智能体时的实际表现。两次运行都走通了
“检索或读取材料—保存事实—绑定证据—证据审核—覆盖评估—生成报告”的主链，
且最终均生成了结构化公开信息调研报告。

从表面产物看，DeepSeek 运行形成了 157 份材料、11 个活跃事实、6 个报告来源，
覆盖 5 个问题中的 4 个；Qwen 运行形成了 8 份材料、1 个活跃事实、1 个报告来源，
仅部分覆盖 1 个问题。DeepSeek 的模型轨迹阶段也更快：558.6 秒完成，Qwen 为
978.1 秒。

但是，这组结果**不能直接证明 DeepSeek 的模型能力优于 Qwen**。两个实验的初始
状态和采集配置不一致：

- Qwen 在轨迹内新建任务，`deep_crawl=false`，从空白任务开始搜索和取证。
- DeepSeek 接手的是一个已执行 60 次搜索、已积累 4 条证据的任务，且
  `deep_crawl=true`；模型轨迹开始前，系统已经完成约 54.5 分钟的深度采集。
- 两次任务的主题文本、部分问题文本、任务 ID 和搜索预算状态也不完全相同。

因此，本报告将本次实验定位为**两套真实运行配置的诊断性对比**，而不是严格的
模型能力排行榜。

当前可以得出的结论是：

1. **Qwen3.8-27B 已具备本地驱动完整工具链的基础能力**，能自主规划问题、搜索、
   抓取、保存事实和证据并结束任务；但在长任务中容易围绕少数事实反复调用，
   事实转化率和跨问题覆盖较低。
2. **DeepSeek-V4-Flash 更擅长消费已有材料、形成原子事实并主动修正过宽事实**，
   在富材料状态下能产出更完整的报告；但上下文和 Token 消耗明显更高，并存在
   搜索预算耗尽后反复评估、继续尝试的低效循环。
3. **系统瓶颈已经不只是模型大小**。任务初始状态、深度采集、搜索预算、问题级
   调度、上下文组织和停止策略会显著影响结果，当前影响甚至大于模型差异。
4. **现阶段不应仅凭本轮结果决定淘汰本地模型**。应先完成同任务快照、同材料、
   同预算的冻结语料对照，再做相同联网配置的重复实验。
5. 工程上建议采用**本地模型为主、强模型按需升级**的分层方案：Qwen 负责常规
   材料筛选、阅读、事实候选和报告草拟；仅将高难度缺口规划、冲突裁决或最终
   关键结论复核升级到云端模型。

### 3.1 两次实验不是同起点实验

| 对比条件 | Qwen3.8-27B | DeepSeek-V4-Flash | 是否一致 |
| --- | --- | --- | --- |
| 主题 | 量子计算产业发展情况 | 量子计算产业发展状况 | 基本一致但不完全相同 |
| 核心问题数 | 5 | 5 | 一致 |
| 任务来源 | 轨迹内调用 `intel_plan` 新建 | 轨迹开始前已经存在 | 不一致 |
| 深度采集 | 关闭 | 开启 | 不一致 |
| 轨迹开始时搜索次数 | 新任务为 0 | 已达 60 次上限 | 不一致 |
| 轨迹开始时证据数 | 新任务为 0 | 已有 4 条 | 不一致 |
| 轨迹开始前材料 | 无可确认的预置材料 | 已完成深度采集 | 不一致 |
| 采集规模上限 | 未执行深度采集 | 深度 3、最多 150 URL | 不一致 |

| 报告深度 | standard | standard | 一致 |

Qwen 轨迹在 14:26:08 开始，模型于轨迹第 2 步调用 `intel_plan`，并在
14:26:24 创建最终研究任务。DeepSeek 任务在 14:49:41 创建，深度采集于
15:44:08 结束，模型轨迹在 15:45:19 才开始。也就是说，DeepSeek 模型真正
开始操作时，系统已经进行了约 54.5 分钟的采集工作。

### 3.2 三类指标的使用规则

为避免错误归因，本文将指标分为三类：

| 指标类别 | 典型指标 | 本报告用途 |
| --- | --- | --- |
| 可直接比较 | 模型调用次数、轨迹内 Token、单次延迟、重复调用 | 描述模型与当前上下文组合的执行效率 |
| 仅描述、不做模型归因 | 材料数、可读材料数、媒体格式、报告来源数 | 描述两套端到端配置的实际产物 |
| 暂不可比较 | 搜索召回率、事实覆盖率、最终报告完整度 | 等完成同起点复现实验后用于选模 |

因此，“DeepSeek 收集到更多材料”首先说明深度采集配置有效，不能单独证明
DeepSeek 搜索能力更强；“Qwen Token 更少”也可能部分来自任务材料较少，不能
单独证明其上下文效率更高。

只看模型轨迹会低估真实任务时延。

DeepSeek 任务的 148 条采集队列中，97 条完成、14 条复用缓存、25 条被
robots.txt 拒绝、8 条因 HTTP 状态跳过、4 条失败。已识别的媒体类型包括
96 个 HTML、2 个 PDF、11 个 JPEG、1 个 PNG 和 1 个 MP4；最终可用材料摘要
中包括 103 个 HTML、2 个 PDF 和 1 个 JPEG。

51 条不可用材料的主要原因是：robots.txt 拒绝 25 条、OCR 文本质量不足
11 条、HTTP 错误 8 条、SSL 错误 2 条、视频转写质量不足 1 条、浏览器不可用
1 条，其余 3 条为其他采集或复用状态问题。

这组数据说明递归采集和多媒体归档链已经实际工作，但也说明“采得广”还没有
自然转化为“有效材料比例高”：DeepSeek 任务中 100 份材料仅获二星，51 份仅获
一星，真正建议优先阅读的五星材料只有 6 份。后续优化重点应从单纯增加 URL 数，
转向搜索前的主题约束、采集队列优先级和采集后的相关性筛选。

### 5.2 事实与证据转化

| 指标 | Qwen3.8-27B | DeepSeek-V4-Flash |
| --- | ---: | ---: |
| 最终活跃事实 | 1 | 11 |
| 完全覆盖事实 | 0 | 1 |
| 最终任务证据数 | 3 | 17 |
| 轨迹内 `fact_save` | 6 次、4 个不同陈述 | 13 次、13 个不同陈述 |
| 轨迹内 `evidence_save` | 7 次、6 个不同组合 | 19 次、18 个不同组合 |
| `fact_supersede` | 0 | 6 次 |
| 最终覆盖等级 | insufficient | insufficient |
| 停止原因 | no_progress | no_progress |

Qwen 曾连续 3 次保存同一个 IBM 处理器事实，并多次围绕同一政府投资数字搜索、
抓取和审核。最终只有“截至 2025 年 4 月全球政府累计投入 100 亿美元”进入报告，
且只有 Wikipedia 一个独立来源组，没有达到“两组独立来源且至少一组高质量来源”
的标准。

DeepSeek 在轨迹内形成了更多互不相同的事实，并使用 `fact_supersede` 将引文没有
完整覆盖的时间限定、适用范围等内容缩窄。该行为说明模型能够理解证据审核反馈，
并将过宽事实改写为更可验证的原子事实。不过，最终 11 个活跃事实中只有 1 个达到
完整覆盖条件，多数仍是单源事实，不能把“事实数量多”解释为“证据质量已经达标”。

### 5.3 问题覆盖

| 核心问题 | Qwen3.8-27B | DeepSeek-V4-Flash |
| --- | --- | --- |
| 技术路线与关键指标 | 未回答 | 部分回答，5 个事实、0 个完全覆盖 |
| 市场规模、投融资和玩家 | 部分回答，1 个事实 | 未回答 |
| 商业化和 QaaS | 未回答 | 部分回答，1 个事实 |
| 各国政策与投入 | 未回答 | 部分回答，1 个事实 |
| 技术瓶颈与量子安全 | 未回答 | 部分回答，4 个事实、1 个完全覆盖 |

DeepSeek 的覆盖面明显更广，但其市场规模和投融资问题完全缺失。这恰好是模型轨迹
开始时尝试搜索的方向，而任务的搜索预算已经耗尽。整个轨迹中系统产生了 17 次
`QUERY_BUDGET_EXHAUSTED` 策略判断，模型又执行了 7 次覆盖评估，最终 gap score
从轨迹开始时的 10 上升到 18。

这里不能把 gap score 上升直接解释为质量下降。覆盖评分会随着新增事实暴露更多
独立来源、高质量来源和问题完整性缺口，事实越多，未满足条件的累计缺口也可能
越大。当前 gap score 更接近“剩余工作量”而不是可横向比较的百分制质量分。

## 六、最终报告质量对比

### 6.1 Qwen 报告

Qwen 报告共 81 行、7,100 字节，结构完整，包括执行摘要、调研范围、五个核心
问题、分歧与不确定性、局限、材料导读和来源目录。报告只形成 1 条可呈现结论，
引用 1 个 Wikipedia 来源；其余 4 个问题诚实标注为“未形成可验证结论”。

优点：

- 没有为填满报告而虚构结论；
- 明确暴露单源、高质量来源不足和未覆盖问题；
- 引用能够回溯到归档材料；
- 生成了五星阅读推荐和材料摘要。

不足：

- 研究覆盖严重不足，无法作为完整产业调研报告交付；
- 大量搜索调用没有转化为可用事实；
- 唯一核心结论来自 Wikipedia，来源质量不满足任务标准；
- 报告的“综合结论”为空。

### 6.2 DeepSeek 报告

DeepSeek 报告共 107 行、13,534 字节，正文呈现 9 条结论，覆盖技术路线、QaaS、
政策和量子安全 4 个方向，引用 Google Quantum AI、IBM、NIST、新华网、中国科大
等 6 个来源。材料导读列出 6 份五星材料，并对 151 份低相关材料做折叠处理。

优点：

- 结果更接近可阅读的专题调研初稿；
- 一手机构、政府和专业机构来源比例高于 Qwen 报告；
- 能通过事实替换修正引文没有完整支撑的表述；
- 材料导读可以帮助用户优先阅读少量高价值来源。

不足：

- 市场规模、投融资和竞争格局这一核心问题完全没有结论；
- 11 个活跃事实中只有 1 个完全满足覆盖标准，多数结论仍为单源；
- “联合国设立国际量子年”等事实与“各国重大政策和投入”的问题只有弱关联，
  体现出问题—事实映射仍可收紧；
- 报告的“综合结论”同样为空；
- 材料数量很大，但高推荐材料仅 6 份，采集噪声较高。

### 6.3 共同问题

两份报告都能诚实呈现证据缺口，这是系统的重要优点。但共同存在以下产品问题：

1. “综合结论”章节为空，降低了报告的管理阅读价值。
2. 报告完成状态为 `with_gaps`，覆盖仍为 `insufficient`，却仍进入 `done`；
   系统需要区分“正常完成”“有缺口交付”和“因无进展停止”。
3. 来源数量和事实数量不足以回答“产业发展情况”这一宽主题。
4. 现有报告强调逐问题列举事实，但缺少产业格局、趋势、判断和下一步阅读路径的
   跨问题综合。
5. 原始运行目录没有保存报告副本和完整状态，长期复盘存在依赖可变运行目录的风险。

## 七、两个模型各自暴露的问题

### 7.1 Qwen3.8-27B

#### 问题一：搜索多、事实转化少

Qwen 执行了 20 次搜索类调用、11 次网页抓取和 11 次文档读取，但最终只有 1 个
活跃事实进入覆盖评估。主要问题不在于完全不会调用工具，而在于不能稳定完成
“搜索结果—优先来源—正文读取—原子事实—精确引文”的连续转化。

建议：由系统确定性控制每个问题的最小转化漏斗。搜索后必须先对结果排序并选择
可抓取的一手来源；连续若干次搜索未新增文档时，强制转入抓取或切换问题，避免
让模型继续自由搜索。

#### 问题二：围绕单一事实反复操作

Qwen 三次保存相同的 IBM 处理器事实，多次审核同一任务，并围绕“政府投入
100 亿美元”反复寻找证据。重复动作占用了有限调用预算，却没有提升独立来源数。

建议：在工具返回中明确标记“事实已存在”“来源组没有新增”“审核指纹未变化”，
并直接给出允许的下一步动作。对相同事实、文档和引文组合做幂等拦截；覆盖指纹
未变化时禁止立即再次调用 `coverage_eval` 或 `evidence_audit`。

#### 问题三：跨问题调度能力弱

模型长期停留在技术路线和投资数字附近，未能为另外三个问题建立事实。

建议：将调度权更多交给系统。按问题维护搜索、文档、事实、独立来源和缺口预算，
单个问题消耗达到上限后自动轮转；报告前至少确保每个核心问题被主动尝试一次。

#### 问题四：本地推理长尾明显

Qwen 平均调用延迟 14.53 秒，但 P95 达到 41.98 秒，最长 82.78 秒。结合平均约
8.42 Token/s 的观测吞吐，长上下文预填充和服务排队可能已经成为主要等待来源。

建议：对本地双槽推理实施长度感知调度，避免两个长上下文请求同时预填充；工具
操作阶段优先使用 32K/64K 上下文，只有证据综合和最终报告阶段才提升到
128K/256K。上下文中只保留任务状态摘要和当前问题材料，不重复注入全量历史。

### 7.2 DeepSeek-V4-Flash

#### 问题一：高度依赖预采集状态

DeepSeek 的主要优势出现在已经有 106 份可读材料的状态下。本轮没有验证其从空白
任务进行问题规划、深度采集和来源扩展的完整表现。

建议：增加一组空白任务联网实验，以及一组两模型共享冻结材料的实验，分别测量
“搜索规划能力”和“材料理解能力”。

#### 问题二：上下文与 Token 成本高

DeepSeek 总 Token 是 Qwen 的 2.27 倍，平均每次输入约 59.9K，P95 约 96.1K。
较长上下文帮助模型读取更多状态，但也会增加云端费用、网络传输、隐私暴露面和
长期任务延迟。

建议：不要因为配置允许 256K 就持续填充上下文。采用问题级工作集，只发送当前
问题的事实、证据、审核结果和最相关材料；完整任务状态以结构化摘要提供。需要
读取旧材料时通过 `document_search` 和 `document_read` 按需恢复。

#### 问题三：搜索预算耗尽后的循环

DeepSeek 进入轨迹时搜索次数已达 60，系统产生 17 次预算耗尽判断，但模型仍在
覆盖评估、状态查询和有限搜索尝试之间循环，最终以 `no_progress` 结束。

建议：预算耗尽应成为模型可见且不可绕过的状态转换。系统应一次性将任务从
“搜索”切换为“消费现有材料”或“有缺口结束”，并从工具列表或动作约束中暂时
移除搜索类工具，避免每轮重复提醒同一限制。

#### 问题四：事实数量增长快于证据质量

DeepSeek 能快速产生事实，也能主动缩窄事实，但大多数事实仍只有单一来源。
如果继续追求事实数量，gap score 会持续增长，报告看似丰富但达不到正式证据标准。

建议：每个问题先形成少量核心事实，再为核心事实执行定向交叉验证。已有单源事实
时，搜索查询必须围绕“第二个独立来源组”生成，而不是继续扩展新的边缘事实。

## 八、系统级问题与修复优先级

### 8.1 P0：先保证实验可复现和结果可解释

1. **完整封存运行包。** 每次运行目录必须包含 `manifest.json`、模型精确版本、
   服务配置、上下文长度、推理模式、Git commit、任务/采集/文档/事实/证据/审核/
   覆盖快照、最终报告和日志。
2. **禁止复用可变全局状态做模型对比。** 对照实验必须从同一只读任务快照复制出
   独立工作目录，不能让后一个模型读取前一个模型留下的搜索次数和证据。
3. **修正分析脚本的无状态误导。** `analyze_run.py` 在缺少 `state/` 时应显示
   “指标不可用”，不得计算 400%/800% 利用率；运行脚本应优先保证状态被复制，
   而不是让分析脚本回读会变化的 `data/intel/`。
4. **记录真实模型身份。** 除接口别名外，记录用户选择的模型名、服务端返回模型、
   权重版本或发布日期、量化方式、推理/思考模式和服务地址标识。
5. **统一完成语义。** 将 `done/sufficient`、`done/with_gaps`、
   `stopped/no_progress`、`failed` 分开，防止“任务结束”被误读成“调研充分”。

### 8.2 P0：提升搜索到证据的有效转化

1. 按核心问题建立独立预算和轮转规则，防止模型长期占用一个问题。
2. 搜索结果必须经过来源质量、主题相关性、可抓取性和独立域增益排序。
3. 连续搜索未新增可读文档时，强制转为抓取、文档内搜索或切换垂直搜索。
4. 单源事实优先进入交叉验证队列，新增第二独立来源的优先级高于继续扩展边缘事实。
5. 覆盖指纹没有变化时，拦截重复审核和覆盖评估。

### 8.3 P1：优化上下文和本地模型执行

1. 默认使用问题级上下文，不把全部 157 份材料和完整历史反复发送给模型。
2. 将上下文分为固定任务约束、当前问题工作集、压缩任务状态和按需读取材料四层。
3. 工具选择阶段优先使用 32K/64K；证据综合使用 128K；只有确有必要时使用 256K。
4. 双槽本地推理采用“一个长任务加一个短任务”的长度感知调度，避免双长请求竞争。
5. 分别记录排队、预填充、首 Token、decode 和工具执行耗时，定位 82 秒长尾来源。

### 8.4 P1：提升采集质量而不是只增加数量

1. 深度采集队列按问题关键词、锚文本、来源等级、附件类型和独立域增益排序。
2. 对导航页、搜索跳转链接、站内无关图片设置更低优先级，减少 OCR 噪声和
   robots 拒绝浪费。
3. Chromium 运行环境需完成 sandbox 部署验收，不能依赖不安全的 `--no-sandbox`
   作为默认解决方案。
4. 对 PDF、图片和视频分别统计发现数、下载数、成功抽取数、可用文本数和进入证据数，
   避免“已归档媒体”被误当作“已理解媒体”。
5. SSL 失败、HTTP 失败、robots 拒绝和处理器质量不足应分别进入可观测指标和重试策略。

### 8.5 P1：改善报告可用性

1. “综合结论”不得为空，应基于已审核事实生成跨问题摘要；证据不足时也应明确说明
   当前能够判断什么、不能判断什么。
2. 执行摘要应区分“完全回答、部分回答、未回答”，并显示每个问题的独立来源数。
3. 对单源事实增加醒目标识，但不再重复设计额外可信度标签；继续保留 1—5 星阅读推荐。
4. 报告结尾给出建议阅读顺序：优先来源、补充来源和不建议投入时间的低相关材料。

## 九、公平复现实验规范

### 9.1 建议设置两类实验

#### A. 冻结材料实验：评价模型理解和研究推理

两个模型读取完全相同的任务、问题、文档、事实初始状态和工具权限，禁止联网和
新增采集。该实验重点测量：

- 原子事实正确率；
- 引文精确支持率；
- 事实—问题映射准确率；
- 独立来源识别准确率；
- 事实纠错和冲突处理能力；
- 报告完整度和阅读可用性；
- Token、耗时和重复调用。

#### B. 真实联网实验：评价端到端调研能力

两个模型从相同空白任务开始，使用相同搜索提供商、深度采集配置、URL/字节/时间
预算、缓存状态和机器环境。该实验重点测量：

- 搜索结果相关率和有效域数量；
- 一手来源、高质量来源和垂直来源覆盖；
- 搜索到可读文档的转化率；
- 可读文档到证据的转化率；
- 五个问题的完整回答率；
- 端到端用时、模型时间、采集时间和人工复核时间。

### 9.2 固定控制变量

每个模型至少重复运行 3 次，并固定：

- Git commit 和配置文件哈希；
- 核心问题、时间范围、地区和语言；
- `deep_crawl`、最大深度、最大 URL、域名上限和字节预算；
- 模型上下文上限、温度、思考模式和最大轮次；
- 搜索引擎及调用顺序；
- 缓存是否预热；
- 证据标准和停止规则；
- 报告模板与评分表。

联网结果会随时间变化。应在同一时间窗口交错执行
`Qwen-1 → DeepSeek-1 → DeepSeek-2 → Qwen-2`，降低网络时序偏差；同时保留
搜索响应摘要和最终归档文档，以便复核。

### 9.3 建议核心评分表

| 一级指标 | 建议权重 | 量化方法 |
| --- | ---: | --- |
| 问题回答质量 | 25% | 完全回答问题数/总问题数，并由盲审确认 |
| 证据正确性 | 25% | 精确引文支持率、可追溯率、虚构事实数 |
| 搜索覆盖 | 15% | 有效独立域、一手来源、垂直来源和时间覆盖 |
| 材料有效性 | 10% | 相关可读材料/全部材料，五星材料占比 |
| 交叉验证 | 10% | 核心事实达到两个独立来源组的比例 |
| 报告可用性 | 10% | 管理者盲评、阅读推荐有效率、摘要完整度 |
| 执行效率 | 5% | 端到端时间、模型 Token、重复调用和失败率归一化 |

质量指标应作为硬门槛，效率只能在质量合格的模型之间比较。建议最低门槛为：
引用可追溯率 100%、引文支持率不低于 95%、重大虚构为 0、核心问题完全回答率
不低于 85%、需要交叉验证的关键结论执行率 100%。

## 十、部署与选模建议

### 10.1 当前不建议做单模型替代结论

本轮足以证明两个模型都能驱动工具链，但不足以证明“云端一定优于本地”或“本地
已经可以完全替代云端”。决定选模的关键应该是同等输入条件下的证据质量、任务
成功率、运行成本、数据安全和响应时间，而不是单次报告中的材料数量。

### 10.2 建议的分层使用方式

| 任务阶段 | 默认模型/机制 | 升级条件 |
| --- | --- | --- |
| 查询矩阵、队列调度、预算控制 | 确定性系统逻辑 | 不交给模型自由决定 |
| 材料初筛、摘要和阅读推荐 | 本地 Qwen | 低置信或复杂专业材料 |
| 文档内事实候选抽取 | 本地 Qwen | 引文与事实范围多次不一致 |
| 交叉验证查询生成 | 本地 Qwen + 规则 | 连续两轮没有新增独立来源 |
| 冲突裁决和复杂证据审核 | 强模型按需调用 | 高影响事实或来源冲突 |
| 最终报告草拟 | 本地 Qwen | 覆盖充分但综合结论质量未达标 |
| 关键结论终审 | 云端强模型或人工 | 对外正式交付必须执行 |

这种方式能够保留本地部署的数据安全、可控成本和离线能力，同时把昂贵的云端
推理集中在真正需要更强推理的少数步骤。后续若通过蒸馏或微调提升 Qwen 的问题
轮转、事实原子化和证据修正能力，云端升级比例还可以继续下降。

### 10.3 下一轮实验的判定目标

下一轮不追求更多工具调用，而应验证以下三个问题：

1. 在同一冻结材料集上，Qwen 的引文支持率和问题回答率与 DeepSeek 相差多少？
2. 在同一联网预算下，两个模型各自能把多少搜索结果转化为高质量独立证据？
3. 采用问题级上下文后，是否能在不降低质量的前提下，将 DeepSeek 和 Qwen 的
   Token 消耗分别降低至少 30%，并显著减少无进展循环？

达到以上条件后，才适合对本地模型、云端模型和混合方案进行正式成本效益比较。

## 十一、总体判断

本次实验最有价值的发现，不是得出某个模型“胜出”，而是确认了系统已经能够让
不同模型在同一套情报工具链上真实运行，并把模型行为、事实、证据、覆盖和报告
串联起来。与此同时，实验也暴露出当前最大短板：运行条件没有冻结、状态封存不完整、
搜索和采集配置差异过大，导致模型效果与系统效果混在一起。

从现有结果看，DeepSeek-V4-Flash 在富材料条件下表现出更强的事实抽取、证据消费
和自我纠错能力；Qwen3.8-27B 则证明了本地模型具备完整执行基础，并以更低 Token
量完成了自主工具调用。下一阶段应优先强化确定性调度、问题级上下文、证据转化和
实验可复现性，再通过冻结材料和同配置联网实验决定模型分工。这样得到的结论才能
支撑后续本地部署、蒸馏微调和云端替代比例设计。
