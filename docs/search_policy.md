# 情报搜集智能体设计思路与关键能力总结报告

## 1. 总体定位

情报搜集智能体的目标，不应简单定义为“本地部署一个 Deep Research”。

普通 Research Agent 更偏向于：

> 用户提出问题 → 搜索资料 → 阅读资料 → 综合内容 → 给出答案或报告。

而情报搜集智能体更应该关注：

> 用户提出情报目标 → 拆解关键问题 → 系统性探索信息空间 → 发现并获取不同类型资源 → 建立证据 → 识别缺口与冲突 → 持续补充搜索 → 判断搜集是否充分 → 输出完整、可追溯的资料与证据集合。

因此，两者的优化目标存在明显区别：

**Research Agent 更偏“答案质量”，情报搜集智能体更偏“证据搜集质量”。**

最终需要回答的不只是“这个问题的答案是什么”，还包括：

* 搜到了哪些信息？
* 哪些关键问题已经得到覆盖？
* 哪些问题仍然缺乏资料？
* 信息来自哪些来源？
* 多个来源是否真正独立？
* 是否存在转载、引用和传播关系？
* 是否存在冲突信息和反证？
* 为什么继续搜索？
* 为什么最终停止搜索？
* 当前搜集结果到底有多充分？

这构成情报搜集智能体区别于一般云端 Research Agent 的核心定位。

---

## 2. 从通用智能体到情报搜集智能体

一个通用智能体至少需要解决几个基本问题：

**目标、知识、工具、决策、状态、评估和人机协作。**

情报搜集场景则需要针对这些基础能力进行专门优化。

其中最重要的变化是：

> 从“Query 驱动搜索”转变为“目标—关键问题—覆盖缺口驱动搜索”。

用户输入通常只是一个比较宽泛的主题。例如：

> 调查某家公司近年来在人工智能芯片领域的发展情况。

系统不能简单把这句话改写成十几个搜索关键词然后调用搜索引擎。

首先应该形成调查目标，并进一步拆解为若干关键问题，例如：

* 公司基本情况是什么？
* 核心产品和技术路线是什么？
* 产品目前发展到什么阶段？
* 主要客户和合作伙伴有哪些？
* 是否获得融资或政府支持？
* 是否存在重大技术、经营或监管风险？
* 近几年发生了哪些关键事件？
* 外界对其技术能力是否存在争议？

此时，智能体真正执行的对象已经不再是“搜索词”，而是一个个**关键问题（Research Question）**。

搜索 Query 只是回答这些问题的手段。

---

# 3. 关键问题驱动的搜索体系

可以将整个搜集过程抽象为：

**用户目标**

↓

**关键问题集合**

↓

**搜索覆盖规划**

↓

**Query / 来源 / 网站 / 数据源选择**

↓

**资源发现**

↓

**资源获取与解析**

↓

**证据形成**

↓

**覆盖情况更新**

↓

**发现新的知识缺口**

↓

**补充搜索**

↓

**停止判断**

这种结构的重要意义在于：

系统不会因为“已经搜索了十轮”就认为任务完成，而是不断判断：

> 我距离回答这些关键问题，还缺什么？

因此搜索行为本质上成为一种**缺口驱动（Gap-driven）的迭代过程**。

---

# 4. 搜索覆盖矩阵

为了把“搜得充分”从模糊感觉变成可以管理和计算的问题，可以建立搜索覆盖矩阵。

最简单的二维结构是：

| 关键问题   | 官方 | 新闻媒体 | 学术/研究 | 行业资料 | 数据库 | 社交/社区 |
| ------ | -- | ---- | ----- | ---- | --- | ----- |
| 公司基本情况 | ✓  | ✓    | -     | ✓    | ✓   | -     |
| 核心技术   | ✓  | ✓    | ✓     | ✓    | -   | ✓     |
| 客户情况   | △  | ✓    | -     | ✓    | -   | △     |
| 风险问题   | -  | ✓    | ✓     | △    | -   | ✓     |
| 重大事件   | ✓  | ✓    | -     | ✓    | ✓   | ✓     |

矩阵中的一个格子并不简单代表“搜过/没搜过”。

它可以继续记录：

* 搜索次数；
* 命中的资料数量；
* 有效资料数量；
* 有效证据数量；
* 独立来源数量；
* 来源质量；
* 是否存在冲突；
* 是否存在反证；
* 最近一次搜索时间；
* 新增信息增益。

这样，“搜索策略”实际上变成一个覆盖优化问题。

例如系统发现：

> “核心技术”已经存在官网、论文和行业资料支持，而“客户情况”只有媒体报道，没有官方材料和独立来源。

那么下一轮最有价值的动作不是继续泛搜：

> `公司名 客户`

而应该有针对性地寻找：

> 公司公告、客户官网、采购公告、招投标资料、合作伙伴新闻稿等能够独立证明客户关系的资料。

这就是从**Query Optimization**进一步转变为**Coverage Optimization**。

---

# 5. 搜索空间不能局限于搜索引擎

搜索引擎只是整个信息发现体系中的一个入口。

如果系统仅仅接入百度、Bing、Google、SearXNG 等多个搜索引擎，本质上仍然是在同一个搜索层面横向扩张。

更完整的搜索体系应该至少覆盖几个层次。

### 第一层：搜索引擎发现

通过不同搜索引擎发现互联网入口。

同时针对关键问题生成不同查询表达，包括：

* 实体名称；
* 别名；
* 英文名称；
* 产品名称；
* 人员名称；
* 时间限定；
* 文件类型；
* 关系关键词；
* 正面关键词；
* 负面关键词；
* 专业领域术语。

搜索引擎的主要作用是：

**发现入口，而不是完成全部资料搜集。**

### 第二层：站点发现

找到一个高价值网站之后，不应该只处理搜索引擎命中的那个 URL。

系统应该进一步探索：

* 首页；
* 栏目页；
* 新闻中心；
* 公告中心；
* 下载中心；
* 文档中心；
* Sitemap；
* RSS；
* 历史页面；
* 站内搜索；
* 相关子域名。

因此：

> 搜索引擎发现的是“入口”，网站本身才是一个需要进一步探索的信息空间。

### 第三层：实体与关系扩展

搜索过程中不断发现新的实体：

公司 → 子公司 → 产品 → 高管 → 投资机构 → 客户 → 供应商 → 合作伙伴 → 竞争对手 → 监管机构。

新的实体又可以成为新的搜索入口。

因此搜索过程逐渐从“关键词列表”发展成一个**实体关系网络**。

### 第四层：资源发现

进入具体页面以后，还需要进一步寻找页面关联的资源：

* HTML；
* 动态渲染内容；
* PDF；
* Word；
* PPT；
* Excel；
* CSV；
* 图片；
* OCR 内容；
* 音频；
* 视频；
* iframe；
* 附件；
* 下载链接；
* 页面调用的公开接口等。

因此：

> 页面不是最终资料，而是一个资源容器。

这也是前面讨论中一个很重要的设计转变：

**不要首先问“系统支持哪些文件格式”，而应该首先问“这个信息源包含哪些可获取资源”。**

---

# 6. Search 与 Fetch 应明确分离

基于上述设计，可以把搜集模块明确划分为两个阶段：

**Search / Discovery：发现值得获取的信息和资源。**

**Fetch / Acquisition：真正把资源获取下来并进行解析。**

Search 负责：

> 哪里可能存在有价值的信息？

Fetch 负责：

> 已经知道资源在哪里，怎么可靠地拿下来？

例如 Search 得到：

`某公司官网 → 投资者关系 → 2025 年年报 PDF`

Fetch 再根据资源类型选择对应方式：

PDF 下载 → PDF Parser；

静态网页 → HTTP Fetch；

动态网页 → Browser Rendering；

图片 → Download + OCR；

音频 → Download + ASR；

Office → Office Parser。

这样做以后，文件格式就不再需要写死在 Agent 主逻辑里，而可以形成一个可扩展的：

**Fetcher + Parser 插件体系。**

未来增加新的文件类型，本质上只是增加新的资源处理能力，而不需要修改整个搜索架构。

---

# 7. 关键问题不能完全静态

关键问题是整个搜索体系的基础，但这里存在一个明显风险：

> 如果最开始的问题拆错了怎么办？

因此关键问题不能完全固定。

但如果允许模型无限制修改问题树，又容易出现：

* 搜索目标漂移；
* 问题无限膨胀；
* 搜索无法结束；
* 资源消耗失控；
* 同一个问题反复拆分；
* 后续难以评测；
* 难以复现智能体运行过程。

因此比较适合的设计不是“完全动态”，而是**受控动态问题树**。

第一阶段可以采用：

> 初始问题固定。

第二阶段增加：

> 模型可以提出“新增关键问题建议”。

进一步再允许：

> 新增、拆分、合并、降级、升级关键问题。

每一次变化都应该保存：

**触发证据 + 修改原因 + 修改前状态 + 修改后状态。**

例如：

> 原关键问题：公司技术能力如何？

搜索过程中发现该公司宣称已经实现某项先进制程。

系统提出新增问题：

> “该先进制程能力是否已经实际量产？”

原因：

> 现有资料中存在公司宣传，但尚无客户、第三方测试或量产证据支持。

这样问题树的变化本身，也成为情报搜集过程的一部分。

---

# 8. 搜索停止不能依赖模型“感觉差不多”

普通 Agent 很容易出现一种危险的停止方式：

> “现有资料已经比较充分。”

这句话实际上没有什么可验证性。

情报搜集智能体应该建立显式停止条件。

可以综合考虑：

**关键问题覆盖率**

有多少核心问题已经获得有效证据？

**独立来源数量**

一个关键事实是否获得多个真正独立的信息源支持？

**来源类型覆盖**

是否只依赖新闻，还是已经覆盖官方、行业、研究等来源？

**冲突状态**

是否仍然存在重要但未解决的信息冲突？

**新增证据率**

最近几轮搜索还能不能持续发现新的有效证据？

例如：

第一轮新增 31 条有效证据；

第二轮新增 17 条；

第三轮新增 6 条；

第四轮新增 1 条；

第五轮新增 0 条。

此时搜索的边际收益已经明显下降。

因此停止判断可以理解为：

> 核心问题基本覆盖 + 关键问题存在足够独立来源 + 重大冲突得到处理 + 新增有效证据趋近于零 + 搜索预算未出现异常。

相比“搜索 10 轮以后停止”，这种方式显然更适合情报搜集任务。

# 9. 情报搜集智能体的评测体系

如果上述过程被结构化记录，那么智能体就可以建立不同于普通聊天机器人的评测体系。

核心可以回答六个问题。

### 搜得全不全？

可以使用：

**关键问题覆盖率**

例如 10 个关键问题中，8 个达到证据要求：

Coverage = 80%

但不能简单把“找到一个网页”视为覆盖，需要定义最低证据要求。

### 来源丰富不丰富？

统计不同来源类型、网站、机构、语言和地域的覆盖情况。

例如两个智能体都找到 100 篇资料：

Agent A：95 篇来自新闻媒体；

Agent B：包含政府、企业官网、论文、数据库、行业报告和新闻。

显然不能简单认为两者搜集能力相同。

### 来源是否真正独立？

100 篇新闻报道可能全部转载同一个新华社消息。

因此：

**网页数量 ≠ 独立来源数量。**

需要识别：

首发 → 引用 → 转载 → 二次报道。

最终形成来源传播关系。

### 有没有持续发现新东西？

可以定义：

**Evidence Gain / Coverage Gain**

即：

> 每一轮搜索新增了多少有效证据、填补了多少新的覆盖缺口。

这是衡量搜索策略的重要指标。

### 找到的信息可靠吗？

可以进一步统计：

* 官方/原始来源比例；
* 多来源交叉验证比例；
* 无法验证事实比例；
* 冲突发现率；
* 冲突解决率；
* 反证发现情况。

### 搜索效率怎么样？

例如：

Agent A 抓取 100 个资源 → 产生 35 条有效证据；

Agent B 抓取 1000 个资源 → 产生 37 条有效证据。

最终输出质量接近，但搜索成本完全不同。

因此还应该评估：

**有效证据 / Search Query**

**有效证据 / Fetch**

**有效证据 / Token**

**有效证据 / 时间**

这些指标对于未来在本地小模型和受限算力环境部署尤其重要。

# 10. 可观测性应该成为底层能力

可观测性不能简单理解为“多打日志”。

真正需要观察的是智能体的：

**状态、行为、决策依据和结果变化。**

一次完整搜索动作至少应该能够回答：

> 当前要解决哪个关键问题？

> 当前发现了什么覆盖缺口？

> 为什么选择这个搜索策略？

> 为什么生成这个 Query？

> 调用了哪个搜索源？

> 返回了哪些候选结果？

> 为什么选择其中某些 URL 进行 Fetch？

> Fetch 得到了哪些资源？

> Parser 是否成功？

> 从资源中产生了哪些有效证据？

> 哪些证据改变了当前认知？

> 覆盖矩阵发生了什么变化？

> 为什么决定继续搜索或者停止？

因此建议将一次 Agent 行为抽象成统一的 Trace：

**Goal → Question → Gap → Decision → Action → Observation → Evidence → State Update**

例如：

```text
Task
 └── Research Question
      ├── Coverage Gap
      │
      ├── Search Decision
      │    └── Search Query
      │         └── Search Results
      │
      ├── Resource Discovery
      │    ├── HTML
      │    ├── PDF
      │    └── Image
      │
      ├── Fetch / Parse
      │
      ├── Evidence
      │
      └── Coverage Update
```

这样才能真正回答：

> “智能体为什么这么做？”

而不仅仅知道：

> “智能体调用了一次 search()。”

---

# 11. 可观测性与评测实际上是一套基础设施

这两个问题不应该分开设计。

如果运行过程中记录：

* Research Question；
* Search Query；
* Source；
* Search Result；
* Resource；
* Evidence；
* Coverage；
* Decision；
* Token；
* Latency；
* Error；

那么开发阶段可以直接计算：

* Query 有效率；
* Fetch 成功率；
* 资源发现率；
* Parser 成功率；
* Evidence Yield；
* Question Coverage；
* Independent Source Count；
* Evidence Gain；
* Token / Evidence；
* Time / Evidence。

因此可以形成：

> **Trace → Metrics → Evaluation → Optimization**

这对后续使用教师模型产生轨迹数据尤其重要。

因为届时需要的并不只是：

`用户问题 → 教师模型最终答案`

而是更加有价值的：

`任务 → 问题拆解 → 覆盖缺口 → 搜索决策 → Query → 搜索结果 → 证据选择 → 状态更新 → 下一轮搜索 → 停止判断`

这些轨迹可以进一步用于：

* 搜索策略分析；
* Prompt 优化；
* 教师模型与小模型对比；
* 错误归因；
* 蒸馏数据构建；
* 策略模型训练；
* Agent Benchmark。

所以从研发角度看，**可观测性不是最后补上的运维功能，而应该从第一版 Agent 就进入底层数据结构。**

# 12. 最终总体架构

综合以上讨论，可以把情报搜集智能体抽象成下面这条主链：

```text
                     用户情报目标
                          │
                          ▼
                   任务理解与约束
                          │
                          ▼
                     关键问题树
                          │
                          ▼
                    搜索覆盖矩阵
                          │
                  ┌───────┴───────┐
                  ▼               ▼
             覆盖缺口分析      搜索策略选择
                  │               │
                  └───────┬───────┘
                          ▼
                    Search / Discovery
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          搜索引擎       站点探索      实体关系扩展
             │            │            │
             └────────────┼────────────┘
                          ▼
                      资源发现
                          │
        ┌────────┬────────┼────────┬────────┐
        ▼        ▼        ▼        ▼        ▼
       HTML     PDF      Office    Image   Audio/Video
        │        │        │        │        │
        └────────┴────────┼────────┴────────┘
                          ▼
                    Fetch + Parser
                          │
                          ▼
                      证据形成
                          │
                          ▼
                 来源与证据关系治理
                          │
                          ▼
              Coverage / Conflict Update
                          │
                  ┌───────┴────────┐
                  ▼                ▼
               仍有缺口           搜集充分
                  │                │
                  └──重新规划       ▼
                              标准化证据集合
```

整个过程中存在一条贯穿所有模块的横向基础设施：

```text
             Observability / Trace
                      │
     ┌────────────────┼────────────────┐
     ▼                ▼                ▼
  决策轨迹          状态变化          工具调用
     │                │                │
     └────────────────┼────────────────┘
                      ▼
                   Metrics
                      │
                      ▼
                  Evaluation
                      │
                      ▼
              策略优化 / 蒸馏
```

# 13. 核心设计思想总结

如果把今天讨论的内容压缩成几个核心思想，可以概括为：

**第一，从答案导向转向证据导向。**

智能体的主要产物不是一段“看起来正确”的回答，而是一套充分、可信、可追溯的证据集合。

**第二，从 Query 驱动转向关键问题与覆盖缺口驱动。**

Query 只是执行手段。真正控制搜索的是“还有哪些问题没有被充分回答”。

**第三，从网页搜索转向信息空间探索。**

搜索引擎只是入口。网站、目录、实体关系、附件、图片、音视频、公开数据资源共同组成真正的信息空间。

**第四，从文件格式导向转向资源发现导向。**

不是预先假设“我要抓 PDF”，而是先发现一个信息源中存在什么资源，再调用相应 Fetcher 和 Parser。

**第五，从固定流程转向受控自适应搜索。**

关键问题、搜索策略和覆盖状态可以随着新证据变化，但变化必须受到预算、规则和审计约束。

**第六，从搜索次数转向搜索充分性。**

停止搜索不是因为“已经搜了很多”，而是因为覆盖充分、来源独立、重大冲突得到处理，而且新增证据的边际收益已经明显下降。

**第七，把可观测性和评测放到底层。**

每一次“为什么搜、搜什么、发现什么、为什么继续、为什么停止”都应该成为结构化轨迹。

最终，这套系统真正需要优化的不是单纯的“搜索能力”，而是：

> **在有限时间、算力和 Token 预算下，对公开信息空间进行系统探索，并最大化关键问题的有效证据覆盖，同时保证来源独立、过程可追溯、结果可验证。**

这比“本地版 Deep Research”要准确得多，也更能体现专用情报搜集智能体真正值得做的地方。
